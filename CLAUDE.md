## Build conventions

- **Central Package Management is on.** All NuGet versions live in `Directory.Packages.props`. csproj files use `<PackageReference Include="..." />` *without* a `Version=` attribute. Adding a new dependency means editing both files.
- **`TreatWarningsAsErrors=true`** in `Directory.Build.props` — a build warning fails the build.

## Architecture

Four .NET services, communicating only through the filesystem (Maildir) and the SQLite database. The processes are independent — each can be restarted or replaced without affecting the others; keep this isolation when extending.

**There is no GUI.** A SwiftUI menu-bar tray app and the plain-REST `/tray/*` surface it polled were removed once the container became the only deployment in use; `Mcp:EnableTrayEndpoints` and `TrayExposureGuard` went with them. Don't reintroduce an unauthenticated mail-bearing HTTP surface — see `docs/future-ideas.md` "A GUI, if one is ever wanted again" for what it would actually cost.

Notes that the project layout doesn't tell you:

- **Mailvec.Indexer** does *not* call Ollama or any embedding provider. It registers embedding **identity only** (`EmbeddingRegistration.AddMailvecEmbeddingIdentity` — the resolved profile, no transport, no HttpClient, and by construction no credentials), because it can be the first process to create the schema and a fresh database must stamp the resolved profile's space id. Don't "upgrade" it to the full `AddMailvecEmbedding`: hosted-profile registration resolves the bearer key, and the indexer must never hold it.
- **Mailvec.Mcp** — AspNetCore app exposing MCP tools over HTTP on `Mcp:BindAddress` (`127.0.0.1:3333` locally; `0.0.0.0:3333` in the container, where the Cloudflare tunnel is the only ingress and Access is the auth gate). Read-only against the database, except `view_attachment` and `get_attachment_page_image`, which read `.eml` files out of the Maildir. Also serves the monitor endpoints: **`/up`** is the forwarded one (booleans only — the Uptime Kuma probe); **`/health`** is its detailed sibling, served to **loopback callers only** (`Mcp:RestrictHealthToLoopback`, default true) because it discloses the archive path, corpus counts, model identity and the internal Ollama LAN address. Origin authentication of the Cloudflare Access assertion is available but off by default (`Mcp:Access`). See `docs/security.md`.
- **Mailvec.Cli** — admin commands hitting the same DB (including the `eval` / `eval-add` / `eval-import` family for retrieval-quality benchmarking).

## Configuration

Each runnable service has its own `appsettings.json` containing only the sections it needs. **Embedding provider selection** lives in the `Embedding:*` section (named profiles; absent = legacy Ollama derived from `Ollama:*` — see `docs/proposals/embedding-providers.md`). Hosted API keys go in an owner-only file referenced by `Auth:ApiKeyFile`, never in the shared config. Configuration POCOs live in `Mailvec.Core/Options/` and are bound in each service's `Program.cs`. Local overrides go in `appsettings.Local.json` (gitignored) — but the **shared file wins over it** (it's inserted after all appsettings sources), so for the four shared keys below a per-binary Local file is silently ignored; use an env var (highest precedence) for one-off overrides of those. Publish never copies the Local file (`CopyToPublishDirectory=Never`).

**Single source of truth for user-specific settings** lives at `~/Library/Application Support/Mailvec/appsettings.Local.json`, written by `ops/install.sh` and read by every Mailvec binary via `SharedConfig.AddMailvecSharedConfig()` ([SharedConfig.cs](src/Mailvec.Core/Options/SharedConfig.cs)). It holds four of the five settings that used to be duplicated across the launchd plist and the MCPB manifest's `user_config`: `Archive:DatabasePath`, `Ingest:MaildirRoot`, `Ollama:BaseUrl`, `Fastmail:AccountId` (the fifth, `Mcp:LogToolCalls`, stayed env-var-only). **Precedence**: per-binary appsettings → shared file → env vars (highest) — so the MCPB bundle's `Mcp__LogToolCalls` still overrides, and a developer can one-off `Ingest__MaildirRoot=...` in their shell without editing the file.

`ArchiveOptions` (`DatabasePath`, `SqliteVecExtensionPath`) is bound by all four executables (consumed by `ConnectionFactory`). `IngestOptions` (`MaildirRoot`) is bound by the Indexer (scans the Maildir), the CLI (prints the path in `mailvec status`), the MCP server (`view_attachment` reads attachment bytes out of Maildir source files), and — as of the scanned-PDF OCR feature — the **Embedder** (its OCR pass reads `.eml` bytes via `MaildirAttachmentReader` to render scanned PDFs). The Embedder *used* to be the only executable that never touched the filesystem; OCR changed that. The bytes-decode logic is shared: `MaildirAttachmentReader` owns the containment-guarded read, and `AttachmentExtractor` (MCP) delegates to it.

Both indexer and CLI read environment variables with no prefix, so `Ingest__MaildirRoot=/path` works for either. The CLI looks for `appsettings.json` in `AppContext.BaseDirectory`, not the current working directory.

Fetched as a prebuilt loadable (`vec0.dylib` / `vec0.so`) by `ops/fetch-sqlite-vec.sh` and loaded at runtime via `Microsoft.Data.Sqlite`'s extension-loading API. Path comes from `Archive:SqliteVecExtensionPath`. ## Schema & data invariants

`schema/001_initial.sql` is the full schema (v12 baseline). These invariants are enforced at runtime and silent-corruption-prone if bypassed.

- **`metadata.embedding_space_id` + `metadata.embedding_config_hash` (v11) are the embedding-space identity, and they answer different questions.** The space id names the vector space (`ollama:<model>:<dims>` via `EmbeddingSpace.LegacySpaceId`; hosted profiles must assert theirs explicitly — a wire model string is not proof of compatibility). The config hash proves how Mailvec invoked it: a canonical SHA-256 over every vector-affecting setting (space id, wire model, dims, query/document transforms, normalization policy — never secrets, timeouts, or endpoints). It exists for the change no name can see: editing `Ollama:QueryInstructionPrefix` moves query vectors out of the space the stored document vectors live in while model and dims stay identical.
  - **Stamping.** The 011 migration derives the space id from the DB's own stored metadata, **never from config** (config may disagree with what produced the vectors). The hash is stamped only in code (`SchemaMigrator.StampConfigHashIfMissing`) and **only when config agrees with the stored identity** — a hash asserted from mismatched config is a false provenance claim — and an existing stamp is never overwritten by startup stamping. Every write that stamps model/dims stamps space + hash **in the same transaction** (`SwitchEmbeddingModel` does). Compute identity from the resolved profile via `EmbeddingSpace.ForProfile`, **never from `OllamaOptions`**: the canonical serialization (v2) covers all four query/document prefix/suffix transforms, and suffixes exist only on profiles, so an options-derived hash silently ignores them.
  - **Enforcement.** The embedder's per-poll `VerifyEmbeddingModelMatchesSchema` refuses on either mismatch; `ReplaceChunksForMessage` takes `expectedSpaceId`/`expectedConfigHash` and re-checks both inside the write transaction (a switch landing mid-embed must not commit stale-space vectors — same pattern as the model/epoch guards). The read path enforces identity too: `EmbeddingSpaceGuard` refuses semantic/hybrid search before query embedding/KNN on any model/dims/space/hash disagreement (classified `SpaceMismatch`; MCP recommends `mode=keyword`). That guard is deliberately **metadata-only** — a network probe inside every search would couple availability, and unknown-is-never-drift forbids failing on an unreachable listing, so digest and sentinel checks stay on the embedder/health cadence. `/health`, doctor and status report through the **widened** `modelMismatch` flag (the `/up` wire name is locked; absent metadata is unknown, never a mismatch — same rule as `ServiceHeartbeat`). Consequence to remember: **changing the query prefix on an existing DB refuses to embed AND to semantically search** until the setting is reverted or `mailvec switch-model` re-embeds everything — that refusal is the feature. Tests: `VectorSearchServiceTests` guard section.
  - **The third leg is `metadata.embedding_model_digest`** — Ollama tags resolve to content-addressed manifest digests, and a re-pulled tag with different weights is a new vector space wearing the old name, invisible to model, dims, space id AND config hash. Resolution is **exact-tag** (then `name:latest` for tagless config), never the broad same-base match the availability probe uses: with `model:old` and `model:latest` both installed, the broad rule let list ordering decide which digest got stamped (test: `OllamaClientTests.Digest_resolves_latest_never_an_arbitrary_same_base_tag`). It is an **observation, not configuration** — stamped on first sight (once per poll cycle, not per batch; it's an HTTP call), refused on change (remedy: `mailvec switch-model --force`, since the non-forced form sees "same model, nothing to do"), and cleared by `switch-model` in the same transaction as the identity rewrite (a surviving stale digest would refuse the very rebuild it prescribes). No migration: absent = not yet observed, and **null/unobservable is never drift**.
  - **Hosted profiles return null from `IEmbeddingTransport.GetModelArtifactDigestAsync`, so their integrity leg is the sentinel fingerprints** (`EmbeddingSpace.SentinelTexts`, versioned `embedding_sentinel_v1.*` keys): fixed non-mail texts whose embeddings the embedder stamps on first sight and re-compares per poll cycle, refusing below cosine `SentinelMinCosine` (0.999 — set from measurement: 8 repeated Fireworks embeds returned cosine 1.00000000, so the threshold sits orders of magnitude above observed jitter while a real revision swap trips it; re-measure before lowering). Same observation rules as the digest: cleared by `switch-model` in the identity transaction, any classified transport failure skips (never drift), Ollama profiles never run it. Tests: `EmbeddingWorkerTests` sentinel + digest sections, `EmbeddingSpaceIdentityTests.SwitchEmbeddingModel_clears_the_artifact_digest_in_the_same_transaction`, `OllamaClientTests` digest section.

- **`messages.attachment_text` is a denormalized space-join of `attachments.extracted_text`** (any attachment with non-empty text — i.e. status `done` or `ocr`), built by `MessageRepository.BuildAttachmentText` and written in the same transaction as `attachment_names`. It feeds the 6th `messages_fts` column so keyword search hits attachment bodies; if a write path updates `attachments.extracted_text` without rebuilding `messages.attachment_text`, FTS silently drifts and dual-signal RRF fusion stops boosting documents that should match both the BM25 and vector legs.
- **The embedding model is part of the schema.** `chunk_embeddings` declares a fixed dimension, substituted from `Ollama:EmbeddingModel`/`EmbeddingDimensions` on fresh-DB creation by `SchemaMigrator.SubstituteEmbeddingConfig` (each substitution token must appear exactly once in `001_initial.sql`; the migrator throws otherwise). `EmbeddingService.ValidateAndNormalize` checks vector count/width/finiteness against the resolved profile and L2-normalizes any unnormalized vector (vec0 KNN is L2; unit norm is what makes it rank like cosine) — once, for every transport; `EmbeddingWorker` refuses to start if `metadata.embedding_model` disagrees with the resolved profile. **`mailvec switch-model` is the only sanctioned way to change an existing DB's model** — it rebuilds the vec0 table at the new dimension, clears chunks, re-queues every message, and updates metadata in one transaction (see `docs/contributing/embedding-experiments.md`). **Never bypass these checks** — mixing vector spaces silently corrupts similarity scores in ways that look plausible. The seam is two layers (`Mailvec.Core/Embedding/`): **consumers go through `IEmbeddingService`** (purpose-aware — `EmbedQueryAsync` applies the profile's query transform, `EmbedDocumentsAsync` the document transform, `ProbeAsync` classifies readiness), over `IEmbeddingTransport` underneath (`OllamaClient` for the local protocol, `OpenAiCompatibleTransport` for hosted — Fireworks/OpenAI/Baseten are PROFILES over the one class, never per-vendor subclasses). Transports return RAW vectors; the mathematical contract is enforced once in `ValidateAndNormalize` (load-bearing for Fireworks, whose vectors arrive at norm ~65). Registration is centralized in `EmbeddingRegistration.AddMailvecEmbedding` (the `VisionRegistration` pattern) so Embedder, MCP and CLI can't resolve different providers or text transforms — the query prefix is applied in `EmbeddingService`, never at call sites. Transport failures throw the classified `EmbeddingException`, whose `Backpressure`/`AuthOrConfig`/`ModelUnavailable` are provider-wide and never count as quarantine strikes against a message (test: `EmbeddingWorkerTests.Backpressure_failures_never_quarantine_however_long_they_last`).
- **FTS5 sync is trigger-driven.** `messages_ai`/`messages_ad`/`messages_au` keep `messages_fts` in lockstep with `messages`. Don't bypass the triggers with raw inserts into `messages_fts`.
- **`vec0` must load before the schema applies**, because `001_initial.sql` declares `chunk_embeddings` as a `vec0(...)` virtual table. `ConnectionFactory` loads the extension on every `Open()`. The native library is copied into each project's `bin/.../runtimes/<rid>/native/` by `Directory.Build.props` (a `runtimes/**` glob that no-ops when the fetch script hasn't run).
- **`chunk_embeddings` has no foreign key to `chunks`** because vec0 virtual tables don't support FKs. `ChunkRepository.DeleteChunks` deletes from both tables explicitly inside one transaction. Don't `DELETE FROM chunks` directly without also cleaning `chunk_embeddings`.
- **Vector serialization to sqlite-vec.** `FLOAT[N]` columns are stored as packed little-endian float32 bytes. `VectorBlob.Serialize/Deserialize` in `ChunkRepository.cs` is the only place that does this conversion — keep all sqlite-vec writes/reads going through it.
- **`PRAGMA journal_mode = WAL` must be applied via `ExecuteScalar`, not `ExecuteNonQuery`.** Microsoft.Data.Sqlite silently no-ops result-returning pragmas under `ExecuteNonQuery`, so the WAL pragma in `001_initial.sql` was *not actually setting WAL mode* — DBs were running in plain rollback-journal `delete` mode. Confirmed by reading header bytes 18-19 (`01 01` for journal, `02 02` for WAL). Fix lives in `ConnectionFactory.Open()`: a per-connection `PRAGMA journal_mode = WAL;` via `ExecuteScalar`, idempotent and self-healing for any DB created before the fix landed. Don't move this back into the migration script.
- **`Microsoft.Data.Sqlite.ExecuteNonQuery` silently stops at the first `CREATE TRIGGER ... BEGIN ... END;`.** The internal trigger semicolons confuse its statement iterator. `SqlScriptSplitter` tokenises scripts itself (BEGIN/END depth-tracking) and executes one statement at a time. Don't go back to `ExecuteNonQuery`-on-the-whole-script.

Attachment text:

- **`attachments.extracted_text` / `extracted_at` / `extraction_status`** hold the recovered plain text. `chunks.source` ('body' | 'attachment') + `chunks.attachment_id` let search results trace back to a specific document.
- **`extraction_status` is a stable enum** declared as constants on `AttachmentTextExtractor`: `done`, `ocr`, `no_text`, `unsupported`, `oversize`, `encrypted`, `failed`. Persist these values verbatim — they're surfaced through `get_email`'s `AttachmentInfo.ExtractionStatus` so Claude can tell the user "I couldn't read this PDF because it was encrypted". **`ocr`** means a scanned PDF stuck at `no_text` was later recovered by the **embedder's** vision-model OCR pass (written by `MessageRepository.SaveOcrText`, not the indexer); it's treated as searchable like `done` (both the FTS `attachment_text` rebuild and `get_email`'s `IndexedForSearch` include it). The embedder OCRs anything at `no_text` that's a PDF, so a re-index that resets a doc to `no_text` self-heals on the next OCR pass. See `docs/contributing/attachment-ocr.md`.
- **An attachment id does not identify a document — every OCR write-back is identity-guarded.** `attachments.id` is an `INTEGER PRIMARY KEY` *without* `AUTOINCREMENT`, so a row deleted from the tail of the rowid space hands its id to the next insert, possibly one belonging to a different message. The OCR pass selects a candidate and writes back minutes later (file read + page renders + vision calls in between), and a status-only guard can't tell "still my document" from "a different pending scan that inherited this rowid" — a freshly parsed scanned PDF lands at exactly `no_text` (an image at `unsupported`). `SaveOcrText` / `MarkAttachmentOcrFailed` / `MarkAttachmentImageNoText` therefore take the whole `OcrCandidate` and match `MessageRepository.OcrIdentityMatch`: same id, `message_id` and `part_index`, and the parent's `content_hash` unmoved (it covers the multipart structure, so it decides whether the bytes at that part are still the document we OCR'd; `IS`, not `=`, so legacy NULL hashes match). **Pass the candidate through — never just the id.** A skipped write is always safe: the replacement row is re-selected next cycle against its own snapshot. Getting it wrong marks a document searchable under text it doesn't contain, with `attachment_text` rebuilt for the *snapshot's* parent (the FTS drift the denormalization invariant above exists to prevent), and nothing left to re-trigger. **The same identity rule governs the in-memory counters and what a guarded write reports**: `AttachmentOcrService._visionFailures` keys on `(attachment_id, message_id, part_index, parent content_hash)`, so a replacement document can't inherit the previous occupant's strikes; and the three write methods return `OcrWriteOutcome` (`Committed` / `Stale`) rather than void, because a skipped write was otherwise indistinguishable from a committed one — the pass counted `done`, cleared strikes, logged success, and told the worker OCR had produced work. **Count committed transitions only.** Tests: `MessageRepositoryOcrTests.SaveOcrText_does_not_write_onto_a_row_id_reused_by_another_message` / `..._after_the_parent_content_changed` / `SaveOcrText_reports_Stale_when_the_guard_matches_nothing`, `AttachmentOcrServiceTests.Strikes_do_not_carry_across_a_document_change_on_the_same_row`.
- **The same snapshot rule applies to `mailvec extract-attachments`, and its staging exists for a second reason.** Parsing AND extraction both happen *outside* the write transaction (stage 1 parse, stage 2 read the candidate set, stage 3 extract with no connection open, stage 4 revalidate + apply). Not tidiness: `BeginTransaction()` issues `BEGIN IMMEDIATE`, so a transaction opened around the extract loop holds SQLite's single writer slot across every MIME decode and PdfPig/OpenXml parse, stalling the indexer, embedder, OCR write-back, maintenance commands and MCP startup migration for as long as the document takes (it used to do exactly that, under a comment claiming otherwise). **If you need a value from the database mid-extraction, fetch it in stage 2, never inside the tx.** Pinned by `ExtractAttachmentsCommandTests.Extraction_runs_with_the_writer_lock_free`, which probes for the lock from inside the extractor. The out-of-transaction parse also leaves a window for a concurrent indexer re-parse — results are mapped onto rows by `part_index` — so `ExtractAttachmentsCommand.MessageSnapshotUnchanged` re-checks the message's `content_hash` + Maildir location inside the transaction and commits nothing on a mismatch (reported in the run summary, never silently). Default mode is additionally self-guarding (its candidate predicate is `extraction_status IS NULL` and the indexer always writes a non-null status), so the reachable exposure is the `--reextract-*` modes, whose predicates match on content-type/filename regardless of status. `backfill-inline-images` needs no equivalent: `AddInlineAttachments` is `INSERT OR IGNORE` against `UNIQUE(message_id, part_index)`.
- **A missing Maildir source is STALE, never `failed`.** `extract-attachments` reports and skips a message whose `.eml` isn't at the recorded path, leaving its attachments at `extraction_status IS NULL` for a later run. Stamping them `failed` (as it used to) is silent data loss on an ordinary mbsync rename: the path vanishes while the bytes live on unchanged at the new path, the unchanged content means `Upsert` never calls `ReplaceAttachments` (so the stamps survive the rescan), and the default candidate predicate is `extraction_status IS NULL` (so nothing revisits them) — permanently unsearchable, no error, nothing left to re-trigger. Re-attempting a genuinely-deleted message costs one `File.Exists` per run, the right trade; the run summary reports the count so a bounded run can't read as full coverage. Tests: `ExtractAttachmentsCommandTests.Missing_eml_file_leaves_attachments_untouched_for_a_later_run` / `A_second_run_after_the_source_reappears_extracts_normally`.
- **Office formats are ZIP containers, so `Indexer:AttachmentMaxBytes` is not a bound on the parse.** DOCX/XLSX/PPTX are opened through `AttachmentTextExtractor.OfficeOpenSettings`, which sets `MaxCharactersInPart` — **never 0, the SDK's "unlimited"**. Measured before it existed: a **0.95 MB** DOCX allocated **2.45 GB** and took 9.1 s, past the indexer's 2 GB container limit at 1/26th of the 25 MB input ceiling; with the setting it throws in 0.4 s having allocated 66 MB. **`MaxExtractedTextChars` is not protection here** and reading it as such is the trap — the break fires only after the whole part DOM is materialized, so the code looks bounded while allocating without limit. The consequence is a wedge, not a crash: extraction runs inside the scan before any row is written, so an OOM-kill commits nothing, `restart: unless-stopped` brings the indexer back, and it parses the same attachment forever — all indexing stopped, by anyone who can send the user mail. Tests: `OfficePartLimitTests` (a valid small package AND a bomb per format, so a malformed-package false pass is impossible).
- **OCR candidate selection needs a cursor; the read backoff is not a fairness guarantee.** `AttachmentOcrService` sweeps the id space from `_pdfCursor`/`_imageCursor` because both candidate queries are `ORDER BY a.id LIMIT` and a failed byte read leaves the row's status untouched — so selecting from the lowest id every cycle re-picks the same head forever. `_readBackoffUntilCycle` only raises the threshold: with batch `N` and backoff `K` it clears `N × K` blockers in `K` cycles, at which point the first is selectable again (20 at the defaults, ~10 with both passes sharing `_cycle`). The cursor must advance past rows attempted *and* skipped-for-backoff, but **not** past rows the over-fetch returned and the scan never examined. A poison document retires after `MaxVisionAttempts` **sweeps**, not cycles — no test here may assume selection order. See [`docs/contributing/attachment-ocr.md`](docs/contributing/attachment-ocr.md).
- **Extraction libraries are pure-managed.** PDF via `PdfPig` (Apache 2.0); DOCX / XLSX / PPTX via `DocumentFormat.OpenXml` (MIT); iCalendar (`.ics`) and vCard (`.vcf`) via hand-rolled unfold/field extractors; plain text decoded via the declared MIME charset first (strict), then UTF-8, then Windows-1252 (charset-ladder note in `docs/contributing/attachment-indexing.md`; the pre-fix mojibake backfill is `mailvec extract-attachments --reextract-text`). No native deps, no shell-out, no OCR — **this applies to the indexer's text-extraction path only**, and "no OCR" is no longer absolute: the embedder OCRs scanned PDFs out of band (below). Scanned PDFs come back as `extraction_status='no_text'` and the indexer never retries them. The full supported-format list plus every size/dimension/filetype skip gate and its rationale live in [`docs/contributing/attachment-indexing.md`](docs/contributing/attachment-indexing.md).
- **Rasterisation is the one native dep in the read path besides `sqlite-vec`, and it stays in `Mailvec.Pdf`.** `PdfRenderer` (via `PDFtoImage` = PDFium + SkiaSharp) is referenced **only** by `Mailvec.Mcp` (`get_attachment_page_image`) and `Mailvec.Embedder` (the OCR pass) — keep it out of Core/Indexer/Cli. Platform-gated with `[SupportedOSPlatform]` to macOS/Linux/Windows; native assets for `osx-arm64`/`osx-x64`/`linux-x64`/`linux-arm64` come transitively through NuGet (no fetch script, unlike `vec0.dylib`) and bloat the self-contained MCPB bundle. The renderer caps the long edge at 1536px (downscale-only) and encodes JPEG q85 on a white background — a fixed-DPI PNG let a large-MediaBox scan balloon to ~20MB, pointless since Claude downsamples to ~1568px anyway. `ImageRenderer` normalises **image attachments** for the same OCR pass: SkiaSharp decodes JPEG/PNG/etc., but its native build ships no TIFF codec, so TIFF is decoded via the pure-managed `BitMiracle.LibTiff.NET` (magic-byte routed, no native dep — works on the Linux target). HEIC stays unsupported (would need native libheif) and returns null → `failed`.

- **Scanned-PDF OCR (the embedder).** Image-only PDFs land at `extraction_status='no_text'` from the indexer (pure-managed PdfPig can't read them). The embedder's OCR pass (`AttachmentOcrService`, behind `Embedder:OcrEnabled`, default on) then renders each page (`PdfRenderer`) and transcribes it through `IVisionClient`, writes the text back as `status='ocr'`, and re-queues the message so it's embedded + FTS-indexed. **Two providers, selected by `Vision:Provider`** (`ollama` default — the local `Ollama:VisionModel`, `qwen2.5vl:7b`; or `mistral` — the hosted mistral-ocr API, incl. an Azure AI Foundry deployment). Registration is centralised in `VisionRegistration.AddMailvecVision` so the Embedder, Cli and Mcp can't drift onto different providers. Quality is near-identical (see `docs/contributing/ocr-bakeoff-2026-08-06.md`); the hosted provider is 5–8x faster and sends mail content off-network.
- **Vision failures are a four-way taxonomy, and collapsing it back to two destroys documents.** `VisionFailureKind` (`Transient` / `Backpressure` / `AuthOrConfig` / `DocumentFatal`) is thrown by both clients and branched on in `AttachmentOcrService.ClassifyVisionFailure`. **Only `Transient` may accrue strikes toward retiring a document to `failed`.** Inferring cause from "did anything else succeed this cycle?" (the original design) is sound for a local model and unsound for a hosted one: a **429 arriving while other documents in the same cycle succeed** reads as a healthy model, counts a strike, and after five throttled cycles stamps a perfectly good scan `failed` — permanently, since no candidate query re-selects a failed row, so a traffic spike would silently burn documents. Backpressure and AuthOrConfig therefore abort the batch counting nothing (the next poll IS the backoff); DocumentFatal retires immediately rather than burning five cycles rediscovering a deterministic refusal. An **unclassified** exception falls through to `Transient`, so a new provider that forgets to classify something degrades to "retry it", never "destroy it". Tests: `AttachmentOcrServiceTests.Backpressure_never_retires_a_document_however_long_it_lasts`, `..._stops_the_batch_rather_than_hammering_the_next_candidate`, `Auth_failure_aborts_without_retiring_anything`, `Document_fatal_retires_immediately_without_burning_five_cycles`.
- **`attachments.ocr_model` (v10) records WHICH engine produced each OCR verdict, and it is written at all three verdicts — not just the transcription.** `SaveOcrText`, `MarkAttachmentImageNoText` and `MarkAttachmentOcrFailed` each stamp it **inside the same identity-guarded UPDATE** that writes the verdict; never as a follow-up write, which could land the engine id on a row the verdict didn't (the hazard `OcrIdentityMatch` exists for). "This engine found no text" and "this engine gave up" are engine-specific judgements — mistral reaches `no_text` via `StripPlaceholders`, Ollama via a `NO_TEXT_FOUND` sentinel, and a `DocumentFatal` from one provider can be a clean read on another — so stamping only the successes would make "retry everything the old engine passed on" inexpressible. **Only a verdict the provider actually produced may name it.** The five paths that retire a document *before* any provider call (unreadable `.eml`, a PDF PDFium can't open, bytes that don't decode as an image, the image dimension/aspect gate) stamp `OcrProvenance.PreProvider` (`'pipeline'`) instead: naming the engine there attributes a verdict to a provider that never saw the document *and* poisons the one query the column exists for, since `--engine ollama:…` would then sweep up corrupt `.eml` files and HEIC images that no provider switch can fix, forever. NULL is also wrong there — that means "provenance unknown" (pre-v10), whereas "no engine was involved" is knowledge, not its absence (`ServiceHeartbeat`'s "Unknown ≠ stale" again). The value for real verdicts comes from `IVisionClient.ModelId` (`provider:model`), **asked of the client that did the work rather than re-read from config** — those are different facts, and they diverge exactly when it matters. It excludes the hosted endpoint URL `VisionRegistration.Describe` appends: deployment state, and it would be baked into thousands of rows. **`reocr` must clear `ocr_model` in the same statement it clears `extracted_text`**, or a reset row keeps a provenance claim about text that no longer exists — permanently, if the re-OCR then retires the document. **`mailvec reocr --engine <id>` is what the column buys** (`--engine unknown` for pre-v10 rows), and the filter is applied inside the candidate query's WHERE so `--limit` slices the filtered set rather than filtering a slice — the other way round, `--limit 1` silently reports "nothing to do" whenever the newest row belongs to the engine you didn't ask for. Tests: `MessageRepositoryOcrTests.Every_OCR_verdict_records_the_engine_that_produced_it` / `A_stale_write_stamps_no_model_because_it_stamps_nothing`, `AttachmentOcrServiceTests.A_pre_provider_failure_is_not_attributed_to_the_vision_engine` / `A_provider_produced_verdict_still_names_the_engine`, `ReocrCommandTests.The_engine_selector_resets_only_that_engine_s_verdicts` / `The_selector_is_applied_before_the_limit_not_after` / `Resetting_clears_the_engine_stamp_along_with_the_text_it_described`.
- **NULL `ocr_model` means "provenance unknown", and nothing infers it.** The v10 migration does not backfill: which provider was configured, and when it changed, is deployment state (`Vision__Provider` in the compose environment) that this repo cannot see, and a **wrong** stamp is worse than none — "re-OCR everything engine X produced" would then silently skip the real X rows and re-run the other engine's. `mailvec backfill-ocr-model --model <id> --before <date>` lets an operator who knows their own history assert it (dry-run by default, `--apply` to write; it won't overwrite a stamp the OCR pass itself observed unless `--overwrite` is passed). It is scoped to `AttachmentOcrSql.BackfillableVerdict` — `'ocr'`, **plus an image at `'no_text'`** — **shared verbatim with `reocr`'s candidate query so the two cannot disagree about what a verdict is**. They did disagree once: `reocr` counted images at `no_text` as completed verdicts while the backfill refused to stamp them, so `--engine unknown` selected 1,380 images the backfill had left NULL and would have re-sent every one to the hosted provider. The indexer can never put an *image* at `no_text` (`ResolveFormat` calls images Unsupported; `BuildResult`'s `no_text` only fires for document formats it parsed), so `MarkAttachmentImageNoText` is its only writer. A **PDF** at `no_text` is the opposite — that IS indexer output — and `failed` also covers corrupt `.eml` files; both stay excluded. Tests: `BackfillOcrModelCommandTests`.
- **Adding a migration means bumping BOTH `SchemaMigrator.LatestSchemaVersion` and the `schema_version` literal inside `001_initial.sql`.** The fresh-database path applies 001 verbatim, so that literal — not the log line's `LatestSchemaVersion` — is what actually stamps a new DB. When they drift, a fresh database is created *with* the newest columns but stamped one version low, and the next startup replays the migration that adds them: `SQLite Error 1: duplicate column name`, an error naming the column and nothing about the stamp that caused it, on the one path (fresh install) least likely to be exercised before shipping. `SchemaMigrator.AssertBaselineStampsLatest` now makes that a named failure at the point of the mistake. Test: `SchemaMigratorTests.The_baseline_schema_stamps_the_version_its_columns_actually_represent`.
- **Switching `Vision:Provider` re-OCRs nothing, and `mailvec reocr` is the only sanctioned way to make it.** The PDF pass selects `no_text` and the image pass `unsupported`, so every document the *previous* engine finished — `ocr`, or an image at `no_text` — is matched by neither query and keeps that engine's output permanently, mistakes included (a hallucinated transcription stays indexed with nothing left to re-trigger). `reocr` resets those to the status their pass selects, and **must** clear `extracted_text`, rebuild `messages.attachment_text`, clear `embedded_at` and bump `embed_epoch` in **one transaction per message** — the first two for the attachment_text denormalization invariant, the second two for the `embed_epoch` re-queue invariant. One transaction per *message*, never one for the run: `BEGIN IMMEDIATE` across thousands of messages holds SQLite's single writer slot and stalls the indexer, embedder and OCR write-back (the trap `extract-attachments` was fixed for). It never touches `done` — that text came from native extraction and is better than any OCR of the same page. Defaults to a dry run because the clear is immediate while replacement text only arrives as the passes drain. **Selection is ordered by the message's `date_sent`, newest first by default (`--order oldest` reverses it) — and the ORDER BY must wrap the column in `datetime()`**, because `date_sent` is `DateTimeOffset.ToString("O")` and one column holds mixed offsets: sorted as text, `…07:13:20-05:00` (12:13Z) lands below `…11:00:00+00:00` (11:00Z), exactly inverted. Same rule the date filters follow. Undated mail sorts last in both directions via an explicit `(date_sent IS NULL)` key — SQLite puts NULLs first on an ascending sort, so "oldest first" would otherwise mean "undated first". Ordering by `a.id` is wrong here: that is insertion order, roughly the initial bulk ingest's Maildir walk, and unrelated to recency. Tests: `ReocrCommandTests`, incl. `Ordering_compares_instants_not_ISO_strings` / `Undated_mail_sorts_last_in_both_directions`.
- **Only the embedder requires vision credentials; MCP and the CLI must degrade, not crash.** `AddMailvecVision(config, requiresCredentials:)` — true in the embedder (starting cleanly and then quietly never OCRing is the worst outcome), false in MCP/CLI, which only probe for `/health` and `doctor`. With `Vision:Provider=mistral` and no key, those get `UnconfiguredVisionClient` and report OCR unavailable. **Don't "tidy" this into validating everywhere**: the compose posture deliberately scopes the API key to the embedder, and throwing in MCP would crashloop the container — killing search and every tool call — over a missing *OCR* key. An unknown provider *name* stays fatal everywhere. Tests: `VisionRegistrationTests`.
- **`MistralOcrClient.StripPlaceholders` is load-bearing, not cosmetic.** mistral-ocr takes no prompt, so there is no `NO_TEXT_FOUND` sentinel to lean on — a textless picture comes back as image placeholders (`![img-0.jpeg](img-0.jpeg)`) and nothing else. Unstripped, the caller sees non-empty text, writes `status='ocr'`, and a photograph becomes searchable by that literal string while `MarkAttachmentImageNoText` never fires. The hosted client also needs a **hard character cap** (`Vision:Mistral:MaxCharsPerCall`) because there is no `num_predict` equivalent; mistral-ocr does repetition-loop, and observed loops were *within* a single pipe-table line, which `CollapseRepeatedLines` cannot catch.
- **The OCR pass runs *before* the embed pass each cycle, and the vision model is not pinned** (loads on demand, `Ollama:VisionKeepAlive` empty → Ollama's default), so it and the embedding model never need to coexist in RAM. Degrades gracefully: if the model isn't pulled it logs + skips (leaving `no_text`); `mailvec doctor` warns. Full design + rationale in [`docs/contributing/attachment-ocr.md`](docs/contributing/attachment-ocr.md).

## Service liveness (heartbeats)

Containers removed the answer to "is the indexer running?" — there's no `launchctl` in compose, and the MCP server can't see a sibling container's state without mounting the Docker socket. Liveness therefore travels through shared state, like everything else here. Source: [`ServiceHeartbeat.cs`](src/Mailvec.Core/Health/ServiceHeartbeat.cs).

- **Three signals, three different questions — don't collapse them.** `heartbeat.<svc>.at` (liveness: the process exists, written by `HeartbeatService` on its **own timer**); `heartbeat.<svc>.cycle_at` (progress: the work loop turned, written by the worker); `EmbedderHealthKeys.*` (batch outcome: the embedder is draining its backlog). Each is the only answer to its question — the batch-outcome keys are deliberately *not* written on an idle cycle, so an idle embedder and a dead one are identical through them; that's why liveness is separate. mbsync mirrors the same split across two files (beat + sync marker) rather than metadata rows; see below.
- **The liveness beat must never be emitted from the work loop.** One Ollama batch or one OCR page render routinely outlives the embedder's 30 s poll interval, so a beat-on-cycle-completion design reports a *busy* worker as dead. That's why `HeartbeatService` is a separate `BackgroundService` with its own `PeriodicTimer` — the decoupling is the design, not an accident of structure.
- **Every writer declares its own cadence** (`interval_s`) alongside the beat, and the reader judges staleness at `StaleAfterMissedBeats` × that. The MCP server binds neither `IndexerOptions` nor `EmbedderOptions`, so the alternative was config coupling that silently desyncs the moment someone retunes a cadence on one side only.
- **Unknown ≠ stale.** No beat on record (fresh DB, worker hasn't beaten yet) reports `Known=false`, never `Stale=true`. A false red on first boot teaches the user to ignore the indicator.
- **`HeartbeatService` calls `EnsureUpToDate()` before its first beat.** `BackgroundService` does *not* guarantee `ExecuteAsync` has run when `StartAsync` returns, and the indexer's worker yields before migrating — so on a fresh DB the first beat hit `no such table: metadata`, got swallowed by the best-effort catch, and left a *running* service reading unknown for a full interval. Concurrent migration is safe by design (`BEGIN IMMEDIATE`; the loser re-reads inside the lock). Test: `HeartbeatService_beats_against_an_unmigrated_database`.
- **mbsync is file-backed, not metadata-backed** — it's a POSIX-sh sidecar with no SQLite. It writes `<maildir-parent>/.mailvec-mbsync-heartbeat` (ISO time + **beat cadence**, `.tmp`-then-`mv`), read by `MbsyncHeartbeatFile`. **The sidecar beats on its own timer, not after each `mbsync -a`** — same rule as `HeartbeatService`: beating on completion reports a *busy* sidecar as dead once a sync outruns `StaleAfterMissedBeats` × the declared cadence (the old 600s sync interval hid this by swallowing a 12-minute backlog pull, so it stayed latent until someone shortened the interval). The second line is therefore the **beat** cadence, never `MBSYNC_INTERVAL_SECONDS`; re-coupling them reintroduces the bug. **The beat sits beside the Maildir root, never inside it**: `MaildirScanner` walks the root and Maildir++ names folders with a leading dot, so a dotfile in the tree risks being parsed as a folder — moving `Ingest:MaildirRoot` to the mount point itself breaks this.
- **That beat is blind to whether the sync WORKED, so mbsync gets a third file.** `<maildir-parent>/.mailvec-mbsync-sync` (ISO time + **sync** interval — the right cadence to declare *here*, unlike in the beat file), written by `sync_ok()` only on exit 0 and read by `MbsyncSyncFile` into `HealthReport.Mail` / `/up`'s `mail.syncStale`. The beat's indifference to outcome is correct — a loop retrying against a dead IMAP server is alive — but it leaves a sidecar whose every sync fails (expired app password, `Patterns` typo, DNS gone) beating happily forever while no mail arrives, and **nothing else in the pipeline can detect that**: `messages.indexed_at` only advances when new mail is actually ingested, so "quiet mailbox" and "sync broken" are identical there. Same liveness/progress/outcome split as above; don't collapse it back into the beat. A **second file, not more lines in the beat**, because `beat()` runs in a subshell that forked before the loop's assignments and can't see them. Staleness uses its own `StaleAfterMissedCycles` (4) with a 30-minute floor — **not** `StaleAfterMissedBeats`, which is shared with the indexer and embedder; the quantity bounded here is time *between successes* (a 12-min pull + 600s interval is already 22 min), and the floor stops the window collapsing if the sync interval is ever shortened.
- **`Mail.SyncStale` never flips `/health`'s 503**, for the same reason liveness doesn't: a sidecar that can't reach Fastmail is *mbsync's* outage, and marking the mcp container unhealthy for it would restart-loop a working server. Monitor it with its own query — `docs/monitoring-uptime-kuma.md` has the consolidated expression.
- **mbsync reports no cycle timestamp** — `MbsyncHeartbeatFile` passes `lastCycleAt: null`. It used to pass the beat time for both axes, honest only while the sidecar beat after each sync; the beat's move onto its own timer left that alias re-reporting `LastBeatAt` as if it were progress. Don't re-alias it to the sync marker either: outcome and progress are different questions.
- **The MCP server has no heartbeat, deliberately.** It's read-only against the DB, and anything reading a heartbeat is by definition talking to a live MCP server.
- **`heartbeat.<svc>.instance` detects a duplicate worker; it must never prevent one.** Nothing serializes two indexers against one database and Maildir — `MessageIngestService`'s coalescing channel is process-local — and two overlapping scans can soft-delete live messages (each reconciles deletions against the paths its own walk enumerated, so mail arriving mid-scan is missing from the older walk's set and reads as deleted). Both processes write this one key, so a `HeartbeatService` reading back an id that isn't its own knows another is beating; it logs and stamps `heartbeat.<svc>.duplicate_seen_at`, surfaced by `ServiceHeartbeat.Read` as `ServiceLiveness.DuplicateInstanceSeen` on a freshness window so it self-clears when the duplicate stops. **Two consecutive sightings are required** — an ordinary restart finds the previous run's id in the slot, and one sighting would fire on every container restart. **Do not escalate this to refuse-to-start**: a container restarting under `restart: unless-stopped` returns while the old beat is still fresh and would refuse to boot, turning the diagnostic into the wedge it warns about. Exclusion (a real interprocess lock around `ScanAll`) was considered and deferred — see `docs/future-ideas.md`.
- **Liveness never flips `/health`'s 503.** `/health` is the mcp container's own compose healthcheck; folding a sibling's death into `Status` would mark *MCP* unhealthy because the *indexer* died — wrong, and actively misleading when triaging. Liveness rides in `HealthReport.Services` for clients to render.

## Indexing & change detection

- **Content-change detection lives in `MessageRepository.Upsert`.** Each parsed message carries a SHA-256 of its body section (computed by `MessageBodyHasher.Hash` over `MimeMessage.Body.WriteTo` — explicitly excludes the top-level header block so post-delivery rewrites like DKIM-Verified don't trigger spurious re-embeds). On upsert we compare against stored `messages.content_hash` in the same transaction and return `UpsertOutcome { Id, ContentChanged }`. Keying off Message-ID (not Maildir path) avoids false positives from renames; hashing `MimeMessage.Body` bytes (not `parsed.BodyText`) decouples from HTML-converter changes — those are handled separately by `mailvec rebuild-bodies --reembed`. Legacy NULL hashes are treated as "not changed" so the migration doesn't mass-clear.
- **Re-queue on content change is atomic with the body write.** The `Upsert` transaction that writes the new `body_text`/`content_hash`/FTS **also** sets `embedded_at = NULL` (gated on the same `$attachments_reset` flag as the attachment refresh, so a no-op rescan leaves it alone). The scanner ([`MaildirScanner.TryIngest`](src/Mailvec.Indexer/Services/MaildirScanner.cs)) still calls `ChunkRepository.ClearEmbeddingsForMessage(id)` when `ContentChanged == true`, but only to drop the stale chunks/vectors promptly — it is no longer load-bearing for correctness. **Don't move the `embedded_at` clear back out of the `Upsert` transaction**: if a crash or `SQLITE_BUSY` lands between the body write and a separate clear, the row keeps a stamped `embedded_at` whose `content_hash` now matches the new body, so no later rescan detects a change and old vectors silently shadow new FTS text forever. Tests: `MessageRepositoryTests.Upsert_clears_embedded_at_atomically_on_content_change` / `Upsert_preserves_embedded_at_on_noop_rescan`.
- **The embedder guards its write against a mid-embed content change.** `EmbeddingWorker` snapshots each message's `content_hash` **and `embed_epoch`** in `EnumerateUnembedded`, spends seconds-to-minutes in Ollama, then passes both to `ChunkRepository.ReplaceChunksForMessage(..., expectedContentHash, checkContentHash: true, expectedEmbedEpoch)`. The write re-reads both inside its (BEGIN IMMEDIATE) transaction and abandons everything — nothing committed — if the row is gone or either value moved. Without this, the indexer committing a body change during the embed call (which reset `embedded_at` and bumped `content_hash`) would be clobbered by stale-body vectors + a fresh `embedded_at` stamp, with no hash delta to ever re-trigger — the same silent divergence from the other side. Skipped messages stay `embedded_at IS NULL` and re-embed against the new body next poll. Test: `ChunkRepositoryTests.ReplaceChunksForMessage_skips_and_preserves_state_when_content_hash_changed`.
- **`messages.embed_epoch` (v7) is the re-queue counter that catches what `content_hash` can't.** Several writers clear `embedded_at` *without* changing `content_hash` — `extract-attachments` (re-embed is its default; `--no-reembed` opts out), `backfill-inline-images`, the OCR write-back (`SaveOcrText`), `rebuild-bodies --reembed`, `reindex`, `switch-model` — so the hash guard alone would let an in-flight embed stamp right over the re-queue: new attachment text keyword-searchable but never vector-embedded, permanently, with nothing to re-trigger. **Every write path that clears `embedded_at` must bump `embed_epoch` in the same transaction — and must clear it in the same transaction that writes the content that made it stale. If you add a new re-queue path, bump the epoch there too.** `extract-attachments` and `rebuild-bodies --reembed` both used to re-queue in a *later* transaction, which for `extract-attachments` was permanent: its default candidate predicate is `extraction_status IS NULL`, and the committed text write makes that non-null, so a failure in between left new attachment text in FTS beside pre-extraction vectors that no re-run would ever re-select. Both now re-queue inline; their bulk `ClearEmbeddings*` calls are prompt stale-vector cleanup only, not load-bearing (same split as `MaildirScanner.TryIngest`). **The embedder's quarantine and strike maps key on that same snapshot** — `(message_id, content_hash, embed_epoch)`, not the id. A message id is an address, not an identity: keyed by id alone, strikes carried across an edit and a quarantine outlived the content that earned it, so editing an unembeddable message (the obvious remedy) silently did nothing until a process restart. `EmbeddingWorker.PruneQuarantine` reconciles against the live rows before each enumeration and releases anything whose snapshot moved. Tests: `EmbeddingWorkerTests.Quarantine_is_released_when_the_message_content_changes`, `ChunkRepositoryTests.ReplaceChunksForMessage_skips_when_embed_epoch_moved`.
- **`sync_state.folder` (v8) is the folder-membership source for search.** A message can live in several folders at once (Gmail's All Mail + every label, Fastmail multi-label, self-CC'd INBOX + Sent) but `messages` keys on `message_id UNIQUE`, so `messages.folder` holds only the attributed primary copy. The folder search filter (`SearchFilterSql.Append`) matches `m.folder OR EXISTS(sync_state)`, and `FolderStats`/`list_folders` count from membership (with a legacy fallback while the column is unpopulated). **Every `SyncStateRepository.Upsert` call must pass the copy's folder** — the parameter has no default on purpose; writing NULL silently shrinks membership and folder filters stop matching that copy.
- **Folder attribution is first-seen-wins, not last-writer.** `MessageRepository.Upsert`'s conflict clause preserves the stored `(folder, maildir_path, maildir_filename)` triple as a unit while the row is live — taking `excluded` made the attributed folder whichever duplicate copy the scan parsed last, flapping between scans. Genuine moves are handled by the scanner's rename-repair pass at the end of the same scan (the stale old path + fresh Message-ID triggers `UpdateMaildirLocation`), which is therefore **load-bearing** — don't remove it. The one exception is resurrection: a soft-deleted row's stored path is exactly the vanished file and its sync_state rows are gone (no repair will ever fire), so on `deleted_at IS NOT NULL` the conflict clause takes the new copy's triple.
- **Content follows attribution: an `Upsert` from a non-attributed copy is a no-op.** Duplicate copies of one Message-ID are not always byte-identical (a mailing-list copy carries an appended footer its Sent counterpart doesn't), so accepting body/attachment content from whichever copy parsed last left the row holding copy A's *location* and copy B's *bytes* — and `view_attachment` / the OCR pass, which resolve `part_index` against the attributed `.eml`, then read a document the metadata never described. It also made `content_hash` alternate between copies, so every rescan that re-parsed both looked like a body change and burned a full re-embed. `Upsert` therefore returns the existing id untouched when the incoming `(maildir_path, maildir_filename)` isn't the stored one (soft-deleted rows exempt — resurrection re-points location *and* content). **Because of this, the rename-repair pass must also call `SyncStateRepository.ClearContentHash` on the survivor's path**: repointing moves attribution but not content, and without forcing a re-parse the survivor rides the mtime fast path forever and the row never re-aligns (this also covers a rename whose file content changed). Costs one re-parse per repoint. **The repoint and the hash clear must commit in ONE transaction** (`UpdateMaildirLocation`'s connection+transaction overload): as two autocommit writes, a crash or `SQLITE_BUSY` between them left the row pointing at the new path while holding the vanished copy's content — permanently and undetectably, because the survivor kept a non-null hash (so the mtime fast path skipped it) and the repair pass skips any row already pointing somewhere live. A failure now leaves the stale `sync_state` entry intact (it's removed only after the repair loop), so the next scan retries. Tests: `MessageRepositoryTests.Repoint_and_hash_clear_roll_back_together` / `..._commit_together` / `Upsert_from_a_copy_at_another_path_does_not_rewrite_the_attributed_row`, `MaildirScannerTests.Divergent_duplicate_copies_*` / `Repointing_to_a_divergent_survivor_realigns_the_stored_content`.
- **Rename detection.** When mbsync renames `new/foo` → `cur/foo:2,S` between scans, the same Message-ID appears at a fresh path while the old `sync_state` row still references the old path. The scanner excludes those from the soft-delete pass by asking `SyncStateRepository.PathsForMessageId` for every recorded path for that Message-ID and keeping the ones its walk actually enumerated (`observedPaths`) — a rename survives because the new path is in that set. This used to be `FreshMessageIds(since: scanStart)`, a `last_seen_at >= cutoff` query; that column is no longer restamped on an unchanged file, so a freshness test here would read every surviving copy as absent and soft-delete live mail.
- **Scans must never overlap.** `MessageIngestService` drives scans from two triggers (the watcher pulse and the periodic timer) but funnels both through a coalescing single-slot channel with a single consumer, so `MaildirScanner.ScanAll` runs one-at-a-time. This is a correctness invariant, not just a perf one: each scan reconciles deletions against the set of paths **its own walk** enumerated (`SyncStateRepository.EntriesNotObserved`), so an older scan still running when a newer one ingests a just-arrived file doesn't have that file in its set and soft-deletes the message it just gained — and `purge-deleted` in that window would hard-delete the row + chunks + vectors. (Before the write-volume fix the hazard ran the other way — last-writer-wins on `last_seen_at`, where the *slower* scan re-stamped an old time and the *newer* scan's cutoff read live files as stale. The mechanism changed; the invariant didn't.) Note a spurious soft-delete is **sticky**: the file is still on disk and unchanged, so every later scan takes the fast path and never clears `deleted_at`. **Don't reintroduce a second concurrent `ScanAll` caller** (e.g. calling it directly from the pulse handler again). `ScanAll` itself stays a synchronous, non-reentrancy-guarded primitive so tests can call it directly; the serialization lives in the driver.
- **The scanner's fast path compares RECORDED file identity, not scan time.** At the top of [`MaildirScanner.TryIngest`](src/Mailvec.Indexer/Services/MaildirScanner.cs): if `sync_state` remembers this exact path AND the file's current mtime + size **equal** the `file_mtime_utc` / `file_size` recorded at the last ingest (v9), the scan returns without re-parsing — without it, every periodic rescan would re-extract every PDF in the archive, the dominant cost on a real corpus. **The equality is the point, and don't relax it back to a comparison against scan time.** It used to be `File.GetLastWriteTimeUtc(file) <= prior.LastSeenAt`, and `last_seen_at` is when Mailvec *looked*, not what it *saw*: any file whose content changed while its mtime stayed at or below the previous scan's start satisfied that test, and since each scan then re-stamped `last_seen_at` without parsing, the skip self-perpetuated (that restamp is gone now, so a NULL-identity row is the one case the fast path still writes — see the write-volume invariant below) — body text, attachments, FTS and vectors pinned forever to content no longer on disk, silently. mbsync can't produce that shape (new files carry current times; flag changes are renames, which land at a fresh path and miss the path-keyed lookup), but every restore tool can — `rsync -a`, `cp -p` and `tar -x` all preserve mtime by design. A NULL identity (pre-v9 rows) falls back to the old comparison for exactly one scan while recording the real identity, so live rows converge after one full scan with no mass re-parse. `ContentHash` must also be non-null: a NULL hash is the "last ingest failed" retry marker. Known residual: a replacement keeping both mtime and byte count is still skipped — only hashing would catch it, and hashing every file every scan is the cost this path exists to avoid. Tests: [`MaildirScannerTests.Rescan_skips_unchanged_files_via_mtime_fast_path`](tests/Mailvec.Indexer.Tests/MaildirScannerTests.cs) / `Rescan_reparses_a_file_whose_content_changed_under_a_restored_mtime`.
- **A scan over an unchanged corpus must write NOTHING, and liveness is proved in memory, not in the database.** The fast path above used to still `Upsert` the `sync_state` row on every hit, purely to restamp `last_seen_at` so the deletion pass wouldn't treat the file as stale. That is one SQLite page per message per scan: on the author's 82k-message corpus, **467 GB/day** into the WAL, measured from the indexer container's cgroup `io.stat` (5.41 MB/s sustained), which in turn kept the checkpointer writing the 4.5 GB main file ~47 times a second. Deletion detection now diffs the tracked paths against an in-memory set of the paths the walk enumerated (`MaildirScanner.observedPaths` → `SyncStateRepository.EntriesNotObserved`), which carries the identical fact for free. **Don't reintroduce a per-file write "so `last_seen_at` stays fresh"** — nothing outside `MaildirScanner` reads that column, and this loop runs over the whole corpus every minute, so any write added here is multiplied by the corpus size and by 1440. The two writes the fast path *does* still make are one-time convergence after a schema upgrade, not per-scan work: a NULL file identity (pre-v9) and a NULL/stale `folder` (pre-v8, and `sync_state` **is** the folder-membership table search reads). Consequences to keep in mind: `last_seen_at` now means *when the row was last written* (renaming it would cost a migration), so **nothing may reintroduce a freshness test against it** — the survivor/rename lookup was `last_seen_at >= scanStart` and had to become "another recorded path for this Message-ID that the walk enumerated" (`PathsForMessageId` ∩ observed), or the first scan after the change would have soft-deleted every renamed and multi-folder message. The set costs ~15 MB at 82k messages and grows linearly. Tests: `MaildirScannerTests.An_unchanged_rescan_writes_nothing` (asserts an exact zero WAL delta — a budget is not safe at this multiplier), `Real_mail_still_lands_on_an_otherwise_unchanged_scan`, `Deletion_is_still_detected_after_many_unchanged_scans`, `A_surviving_copy_is_still_recognised_after_many_unchanged_scans`, `An_mbsync_rename_after_many_unchanged_scans_is_not_a_deletion`, `A_row_missing_its_file_identity_records_one_and_then_goes_quiet`, `A_row_missing_its_folder_records_one_and_then_goes_quiet`.
- **Writing nothing is not the same as holding no lock — the scan must not take SQLite's writer slot on an unchanged file.** `ScanContext.Transaction` BEGINs on first touch and Microsoft.Data.Sqlite issues `BEGIN IMMEDIATE`, so *reading* through it takes the single writer slot. That was survivable only because the old fast path called `NoteWrite` on every file, committing the batch every `BatchSize` rows; once unchanged files stopped writing, nothing committed and an idle scan held the writer lock across the **entire walk** while writing zero bytes — blocking the embedder, the OCR write-back, every maintenance command and MCP's startup migration. Two rules keep it out: `TryIngest`'s per-file `sync_state` read goes through **`ScanContext.CurrentTransaction`** (returns the open transaction or null; never begins one), and the fast path calls **`ctx.Flush()` on any file that needs no write**, so a run of convergence writes can't outlive itself. `BatchSize` still batches consecutive writes, which is all it was ever doing — the parse path `Flush()`es before every `messages.Upsert` anyway. Note the two failure modes need different tests: flushing promptly bounds how *long* the lock is held (probe test) but does nothing about a per-file BEGIN/COMMIT, which is invisible to both a between-files probe and the WAL (an empty transaction dirties no pages) — hence `MaildirScanner.LastScanTransactionsBegun`, which must be **0** on an unchanged scan. Tests: `MaildirScannerTests.An_unchanged_scan_leaves_the_writer_lock_free`, `A_scan_that_writes_releases_the_writer_lock_once_the_writes_stop`, `An_unchanged_scan_never_takes_the_writer_lock_at_all` — verified by mutation, and each catches a different one of the three.
- **The indexer's scan cadence is NOT `Indexer:ScanIntervalSeconds` alone — mbsync drives most of it.** `ScanIntervalSeconds` defaults to **300** (`PeriodicTimer`, anchored at process start, so it fires at a fixed offset past the minute — a constant `:SS` in the logs is this timer, not a coincidence). The much more frequent trigger is the watcher: `ops/mbsyncrc.container.example` sets `SyncState *`, which puts isync's `.mbsyncstate` **inside each Maildir folder** — i.e. inside the `FileSystemWatcher` root — so *every* `mbsync -a` rewrites a watched file and pulses a scan even when no mail moved. At `MBSYNC_INTERVAL_SECONDS` (default **60**, delay-after-completion) that is a scan a minute, drifting rather than phase-locked. Before assuming the scan interval is one knob, check both. Neither is a load-bearing tuning knob now that an unchanged scan is free.
- **Attachment rows are NOT replaced on no-op rescans.** `MessageRepository.Upsert` only calls `ReplaceAttachments` when `IsNewInsert || ContentChanged` (surfaced via `UpsertOutcome.AttachmentsReset`). Without this guard, the `extracted_text` column would be wiped and rebuilt on every scan even when the parent body hadn't changed. The body's `content_hash` covers the multipart structure, so any real attachment delta forces a hash change → reset → re-extraction.
- **Extraction runs inside the indexer's parser.** `MessageParser` takes an optional `AttachmentTextExtractor` ctor dep; the production DI graph in `Mailvec.Indexer/Program.cs` wires it in, while the parameterless ctor (used by tests / the MCP `view_attachment` flow) skips extraction and produces metadata-only attachments. Keep this split — extraction is the only Maildir-touching step that the embedder and MCP server should never invoke.
- **`AttachmentMaxBytes` (default 25MB) is the per-attachment extraction cap.** Anything larger gets `extraction_status='oversize'` and is skipped without decoding. Don't drop this much — a 200MB image-heavy PDF can exhaust RAM during PdfPig parse. Caller declared sizes are checked first (cheap pre-filter), then bytes are re-checked after MIME decode to catch under-reported sizes.
- **`part_index` maps to a MIME part via `MessageParts.Indexable(mime)` — the single source of truth shared by the writer (`MessageParser`) and the reader (`MaildirAttachmentReader`, hence MCP `view_attachment` + the OCR pass).** The set is `mime.Attachments` (disposition=attachment) **first**, then inline image parts (MimeKit's `Attachments` excludes `Content-Disposition: inline` / `cid:` images — commonly real content: photographed docs pasted inline by Apple Mail, forwarded post images). **Inline images are appended after the attachments, not interleaved**, so existing rows' `part_index` never shifts — capturing them is an additive backfill (`mailvec backfill-inline-images`), not a reindex. If the two enumerations ever diverge, `view_attachment`/OCR silently read the wrong bytes for a part. Inline images extract to `unsupported`, so the embedder's image-OCR pass picks them up under its gate. The backfill's candidate set is `body_html LIKE '%cid:%'` — bounded, but it misses inline images in HTML-less mail, a rare edge.
- **The attachment read carries a per-caller size ceiling, and `maxBytes` has NO default anywhere on that path.** `MaildirAttachmentReader.Read`/`ReadBytes` and `AttachmentExtractor.ExtractInMemory` all require it, because the right answer differs per caller and a default silently hands one caller's policy to the next one added: `Extract` (`mailvec extract-attachments`) passes **null** — a user who asked for the file asked for all of it; the MCP viewers pass `Mcp:AttachmentInlineMaxBytes`; the OCR passes pass `Embedder:OcrMaxAttachmentBytes` (both 25 MB, matching `Indexer:AttachmentMaxBytes`, so a document too big to extract text from is also one we won't inline or OCR). **Enforced DURING the decode** via a bounded write stream, never by pre-checking a size: `Content-Length` and `attachments.size_bytes` are claims about the part, and a cap that trusts a claim isn't a cap. Over it, `AttachmentTooLargeException` — terminal for that document, not something to retry.
- **A path that skips the Maildir read must still call `MaildirAttachmentReader.EnsureSourceExists`.** `view_attachment` answers summary-only types (PDF, DOCX, zip) from the `attachments` row without opening the `.eml` — the bytes were decoded in full and discarded, the largest allocation in the tool. But the read it skips is also what answers "is the `.eml` still there?" and what runs the symlink containment guard (both live in the path resolve), so skipping it wholesale returned a confident summary for a message whose file had vanished and quietly retired the disclosure-controlled `FileNotFoundException` the MCP tools translate for the client. One `stat()` buys both back; same rule for any future fast path here. The short-circuit must also resolve name/type through `AttachmentExtractor.ResolveFileName`/`ResolveContentType` rather than the raw columns (mailers send photos as `application/octet-stream`, so reading the column classifies a JPEG as un-inlineable binary and silently stops showing images), and must decline to decide — falling through to the read — on no matching row, unknown size, image, or text-like. Full rationale + tests: [`docs/contributing/attachments.md`](docs/contributing/attachments.md).
- **Building a Maildir path with a bare `Path.Combine` on the stored columns is the bug.** Every read must resolve through `MaildirAttachmentReader` — `Read`/`ReadBytes`/`EnsureSourceExists` for a single part, or the static `ResolveWithinRoot(root, maildirPath, maildirFilename)` for callers that want the whole `.eml` and so can't go through `Read`. That second entry point exists because `mailvec extract-attachments` and `backfill-inline-images` are exactly those callers, and both had quietly exempted themselves from the containment guard — which was one lexical check away from being real, on the two paths a future writer bug would reach first. Refusal is **per-message, not fatal** (a poisoned row must not strand the thousands of good messages behind it in the cursor) and is reported as `REFUSED n` in the run summary, worded as the non-transient thing it is: unlike the missing-source skip, a re-run refuses it again, because it means bad data in `maildir_path`/`maildir_filename`. Tests: `ExtractAttachmentsCommandTests.A_recorded_location_outside_the_maildir_root_is_refused_not_read` / `One_refused_path_does_not_abort_the_rest_of_the_run`, `BackfillInlineImagesCommandTests.A_recorded_location_outside_the_maildir_root_is_refused_not_read`.

## HTML parsing

- **HTML body parsing uses AngleSharp, not MimeKit.** The design doc's reference to MimeKit's `HtmlToText` was wrong (MimeKit doesn't ship that helper). We use AngleSharp's DOM via `Mailvec.Core.Parsing.HtmlToText`, which strips marketing-email noise (hidden preheader text, tracking pixels, image-only and unsubscribe/preferences links, `<address>` and `<footer>` blocks). Output runs through `TextNormalize` and `BoilerplateFilter`. **Tuning detail to remember:** `font-size:0`, `max-height:0`, and `max-width:0` on outer `<td>` wrappers are *layout hacks* (defeating inter-cell whitespace) where the real text lives in inner elements that override the property — never treat these as hide signals or you'll nuke whole branches of legitimate content. Migration when the converter changes: `mailvec rebuild-bodies --reembed` re-derives `body_text` from stored `body_html` and clears `embedded_at`.

## Embedding & chunking

- **Subject is prepended to body before embedding** in `EmbeddingWorker.BuildEmbeddingText`. Newsletters often have a meaningful subject and thin body; replies the other way.
- **Empty-body messages get a stamped `embedded_at` with zero chunks** so the worker doesn't loop on them forever. `ChunkRepository.ReplaceChunksForMessage` accepts empty lists for this reason.
- **Embedder stitches body + attachment chunks into a single per-message chunk stream.** `EmbeddingWorker.BuildChunksForMessage` emits body chunks first (so `chunk_index = 0` is always body when present), then per-attachment chunks tagged `source='attachment'` + `attachment_id=<id>`. `chunk_index` is renumbered sequentially across both sources to satisfy `UNIQUE(message_id, chunk_index)`. Attachment chunks include the filename as a prefix so a query matching the document name still ranks even if the filename token isn't repeated in the body.
- **Chunk size + two layers of overflow handling.** Default `ChunkSizeTokens=200` (chars/4 = 800 char ceiling). The 4-chars/token heuristic is unreliable on real email — punctuation, embedded URLs, base64, marketing-email HTML residue, and non-ASCII can push BPE token counts to 1-2 chars/token, exceeding `mxbai-embed-large`'s 512-token context. Two safety nets:
  1. **Server-side: Ollama's `truncate: true` flag** works for batched `/api/embed` as of Ollama **0.21.2** (this is the floor). The server logs `llm embedding error: the input length exceeds the context length` (INFO-level, not an error response), silently truncates, and returns HTTP 200. Verified empirically by `mailvec audit-embeddings`.
  2. **Client-side fallback in `OllamaClient.EmbedAsync` for HTTP 400**: oversize batches get split in half and recursed; a singleton that still doesn't fit is truncated by 50% repeatedly until it succeeds (down to a 64-char floor). Don't disable this without replacing it with a real tokenizer-based pre-check — it's the safety net if a future Ollama version regresses.

## Search

- **Search filters live on the search services in Core, not on the MCP tool.** `KeywordSearchService.Search`, `VectorSearchService.SearchAsync`, `HybridSearchService.SearchAsync` and `MessageRepository.BrowseByFilters` all accept a `SearchFilters?` (`Folder` / `DateFrom` / `DateTo` / `FromContains` / `FromExact` / `HasAttachments` / `AttachmentType`), and the shared `SearchFilterSql.Append` helper appends WHERE clauses and binds params so filter semantics stay identical across the BM25 leg, the vector leg and the query-less browse path. Hybrid RRF fuses two ranked lists, so post-filtering only one side would skew scores — **don't** post-filter in the MCP layer. `FromExact` takes precedence over `FromContains` when both are set. The `Folder` filter matches a message when **any** of its live copies is in the folder (`m.folder = $folder OR EXISTS` against `sync_state` membership), so a folder-filtered hit can display a different folder than the filter, which is correct.
- **Vector KNN runs before the filter join.** `chunk_embeddings MATCH $vec AND k=$k` returns the raw nearest neighbours; the filter is applied in the joined CTE, so with a restrictive filter a small `k` leaves the post-filter set short even when good matches exist further down the KNN list (this once made bare `mode=semantic` + a folder filter return ~1 result). **`VectorSearchService.SearchByVector` is the single source of truth for the workaround**: it ALWAYS runs the escalation loop — even "unfiltered" KNN is post-filtered by `deleted_at IS NULL` (soft-deletes crowd the ranking until a manual purge) and by the one-row-per-message window — escalating `k` (×8 per round, starting at `max(k, limit)`, bounded by the chunk count) until it has `limit` post-filter hits or has fetched every chunk. Callers pass a base `k` and rely on the loop for correctness; the semantic-mode callers (MCP `search_emails` and the eval ranking source) both use the identical `max(100, limit*5)` base formula — keep them in lockstep, and **don't hand-tune any single caller's `k` to "fix" short results** (fix `SearchByVector` instead; per-caller divergence drifts). **sqlite-vec hard-rejects `k > 4096`** ("k value in knn query too large"); `Vec0MaxK = 4096` caps the escalation and clamps every KNN call. Escalating deeper changes which candidates feed RRF on corpus-selective filters, so re-baseline (`mailvec eval`) after touching this.
- **Date filtering uses `datetime()` for comparison.** Stored `date_sent` is `DateTimeOffset.ToString("O")`, which mixes UTC `Z` and `+HH:mm` offsets. Wrapping both sides in SQLite's `datetime()` normalises them; a raw string compare would silently miss matches across offsets. Messages with NULL `date_sent` are excluded when any date bound is set.
- **`idx_messages_date_sort` (v12) only works while it matches the browse `ORDER BY` term for term — direction included.** The date paths wrap the column in `datetime()`, so no plain-column index can serve them (that is why `idx_messages_date_sent` doesn't); v12 adds an expression index over `(date_sent IS NULL, datetime(date_sent) DESC)`. **Both terms are load-bearing and the `DESC` most of all.** The clause is mixed-direction — `IS NULL` ascending, `datetime(...)` descending — so an index declared both-ASC gets *adopted by the planner and still sorts*: measured on the 81k corpus, browse went from 215 ms unindexed to **9,173 ms**, i.e. 43x worse than no index, while an index on `datetime(date_sent)` alone is never used at all. The correct shape resolves browse in under a millisecond with no sort step. The failure is silent both ways: edit the `ORDER BY` (drop the `IS NULL` key, flip a direction) and the index stops applying; write the index without `DESC` and it applies catastrophically — and the only symptom is latency, with every test green. That is why the clause lives in one place, `MessageRepository.BrowseOrderBy`, and why the test asserts the **query plan** for that const rather than the index's existence (a named index with the wrong column list still exists, so existence-by-name proves nothing): `SchemaMigratorTests.The_date_sort_index_resolves_the_browse_ordering_with_no_sort_step`, verified by mutation — dropping `DESC` and dropping the `IS NULL` key each fail it. Deliberately **not** covered: `list_folders`/`FolderStats` (~490 ms), whose cost is the membership CTE's `UNION`, not date ordering — no index variant moved it. Folder-*filtered* browse is ~36% slower under this index (the planner takes it for ordering, then evaluates the folder `EXISTS` per row) — a priced, accepted trade. Measurements and rejected alternatives: [`docs/future-ideas.md`](docs/future-ideas.md#date-ordering-index-for-datetimedate_sent).
- **`idx_messages_archive_dates` (v13) is PARTIAL, so it applies only while its predicate stays implied by the query's WHERE — and widening it is as wrong as narrowing it.** `GetArchiveStats` returns the archive's oldest/latest `date_sent` **on every search response**, as single-key `ORDER BY datetime(date_sent) <dir> LIMIT 1` subqueries. Neither `idx_messages_date_sent` (plain column, can't serve an expression) nor v12's `idx_messages_date_sort` (leads with `date_sent IS NULL`, which these never mention) can help, so before v13 this was **three full scans of `messages` plus two sorts per search response — 176 ms measured on an 81,732-message corpus** (while a doc comment claimed those bounds were cheap, describing a `MIN/MAX` implementation replaced long before). v13 takes the call to ~61 ms. The predicate is `WHERE deleted_at IS NULL AND date_sent IS NOT NULL`, matched term for term with `MessageRepository.ArchiveStatsSql` — a **const precisely so the test can assert the plan for the real query**. Loosen the query's WHERE and the index silently leaves the plan (latency only, nothing fails). **Widen the index's predicate and it gets worse, not neutral**: at `WHERE deleted_at IS NULL` alone the planner also takes it for the `COUNT(*)` leg, measured ~129 ms — slower than that leg had been with no index at all. Same partial-adoption pathology as v12's both-ASC candidate, and this table has now produced it twice, which is the general lesson: **on `messages`, an index the planner adopts for the wrong leg is worse than no index.** The remaining `COUNT(*)` scan is therefore left alone deliberately; if it ever matters, cache `ArchiveStats` behind a short TTL rather than indexing `deleted_at`. Test: `SchemaMigratorTests.The_archive_stats_date_bounds_resolve_from_the_partial_index` asserts **exactly two** index uses, so both narrowing and widening fail it (verified by mutation in both directions).
- **One row per message** in vector search results. `VectorSearchService` uses a window function (`ROW_NUMBER() OVER ... rn=1`) so the same message can't appear twice from different chunks. Hybrid search relies on this invariant when fusing. Attachment matches don't add rows — the chunk's `source` + `attachment_id` ride along as `VectorHit.ChunkSource` / `MatchedAttachment*`.
- **RRF k=60** in `HybridSearchService.RrfK` — standard from the literature. Don't tune without benchmarking against a real query set.
- **`get_thread` resolves via thread_id, with a special case for lone messages.** `MessageRepository.GetThreadByMessageId` first looks up the requested message, then queries by its `thread_id`. If `thread_id` is NULL (a message that wasn't part of any reference chain), the method returns just that one message rather than empty. Don't "fix" this to require non-null thread_id — singletons are common (notifications, marketing).
- **`SchemaMigrator.EnsureUpToDate()` runs at MCP startup.** If the configured `DatabasePath` doesn't exist, the migrator silently creates a fresh empty schema there. When debugging "no results", first check `mailvec status` to confirm message counts on the same path the MCP server resolved.

## MCP API stability

The MCP tool surface is a **wire contract** — tool names, parameter names, and response field names are locked, and a rename breaks every client at once. The full locked list, plus the `McpSurfaceTests` enforcement mechanism and the transport quirks (stateless HTTP, stdio, Claude Desktop's sandbox), live in [`src/Mailvec.Mcp/CLAUDE.md`](src/Mailvec.Mcp/CLAUDE.md) and load automatically when you work in that project.

Version and release mechanics live in [Releases](#releases) — a tool-surface change is a **minor** bump, and the bump is not yours to make unasked.

Before any change that could shift retrieval ranking (chunk size, RRF k, embedding model, tool-shape tweaks), capture an eval baseline (`mailvec eval --json baselines/<date>.json`) — see `baselines/README.md`. Without it, a quality regression that "looked like a refactor" is invisible until the user notices.

## Operations

- **`/health` is HTTP-mode only.** Stdio has no analog — Claude Desktop sees failures via the `initialize` handshake instead. Endpoint is registered before `MapMcp()` in `Program.cs::RunHttp` and bypasses MCP framing. Logic lives in `Mailvec.Core/Health/HealthService.cs` so the CLI can reuse the snapshot if needed. Returns 503 (not 200) when degraded ("degraded" = Ollama unreachable OR `metadata.embedding_model` disagrees with `Ollama:EmbeddingModel` OR the embedder is stuck — see `HealthService.IsStuck`); don't broaden the degraded set without thinking about false-positive paging cost. Auth boundary is "bind to 127.0.0.1" plus, on the container, the Cloudflare Access gate — optionally validated at the origin via `Mcp:Access` (off by default; `docs/security.md` "Origin authentication"). See the README Security model section before changing the bind address.
- **Ollama ping is bounded by a 5 s linked-CTS, not the embedder's 60 s timeout.** `OllamaClient.PingAsync` wraps the call in `CancellationTokenSource.CreateLinkedTokenSource(ct)` with `CancelAfter(5s)` — 5 s allows a cold model load on the first probe; warm probes return in milliseconds — and only swallows `OperationCanceledException` when the *outer* token wasn't cancelled. This is already at the sensible ceiling; don't raise it further — `/health` is the container's compose healthcheck, which times out at 10 s, and this ping plus the 2 s `/api/tags` follow-up already spend most of that.
- **Logging is in-process (Serilog) and launchd-specific in two ways** — daily/size-capped rolling files, and the stdio MCP deliberately writing to stderr only rather than racing the rolling file. Details: [`docs/install-macos.md`](docs/install-macos.md).
