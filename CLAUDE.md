# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. Stays focused on invariants whose violation is **silent** (silent data corruption, silent contract break, silent quality regression). Loud failures (compile errors, missing files) don't earn a spot.

## Source of truth

The schema is `schema/001_initial.sql` + migrations under `schema/migrations/` — silent-corruption-prone invariants are captured in this file under "Schema & data invariants". `CHANGELOG.md` is the phase-by-phase build history. Design rationale that didn't make it into code lives in `docs/security.md` (threat model) and `docs/future-ideas.md` (deferred work + still-open questions).

**Ops runbooks describe how to VERIFY live state, never what it was.** The Cloudflare and Uptime Kuma configuration lives outside this repo, unversioned, and a doc that asserts it drifts silently. Both `docs/monitoring-uptime-kuma.md` and `docs/remote-access-cloudflare.md` have now been wrong about live state in a way that nearly caused an outage — the monitoring runbook said the six Kuma monitors polled `/up` when all six were on `/health`, and a change that 404s `/health` was about to ship on the strength of that sentence. When you must record observed state, **date it and mark it as observed**, so the reader knows to re-check rather than trust. A verification command ages correctly; a table of last quarter's config does not.

## Common commands

```sh
./ops/fetch-sqlite-vec.sh    # one-time: downloads vec0.dylib into runtimes/<rid>/native/
dotnet test tests/Mailvec.Indexer.Tests --filter "FullyQualifiedName~MaildirScanner"   # single test class
ops/coverage.sh              # runs tests with coverage; HTML at coverage/index.html, Markdown at coverage/SummaryGithub.md
ops/redeploy.sh [indexer|embedder|mcp|cli ...]   # republish + kickstart launchd agents after a code change
ops/stop.sh                                      # bootout the launchd agents without uninstalling
ops/export-db.sh [--out path] [--to host]        # consistent DB snapshot for backup / machine migration
ops/import-db.sh <snapshot.sqlite>               # install a snapshot on this machine (read its header first)
ops/install-all.sh [--no-tray|--no-fetch]        # single-command bootstrap for a new machine
ops/install-tray.sh                              # build + copy to /Applications + launch (calls build-tray.sh)
ops/build-tray.sh                                # XcodeGen → xcodebuild archive → build/Mailvec.Tray.app
```

`Mailvec.slnx` (not `.sln`) is the solution file — .NET 10 emits the new XML format by default.

`dotnet run --project src/Mailvec.<svc>` runs the working-tree code under your terminal — useful for one-off debugging, but **the launchd agents installed by `ops/install.sh` are separate processes** running the published binaries under `~/.local/share/mailvec/<svc>/`. After editing service code, run `ops/redeploy.sh` to push the new binaries and restart the agents — otherwise the live services keep running the old code while `dotnet build` looks like it succeeded. Use `ops/install.sh` only when plist templates change or a config knob needs updating.

## Build conventions

- **Central Package Management is on.** All NuGet versions live in `Directory.Packages.props`. csproj files use `<PackageReference Include="..." />` *without* a `Version=` attribute. Adding a new dependency means editing both files.
- **`TreatWarningsAsErrors=true`** in `Directory.Build.props` — a build warning fails the build.

## Architecture

Four .NET services + a SwiftUI tray app, communicating only through the filesystem (Maildir) and the SQLite database. The four .NET processes are independent — each can be restarted or replaced without affecting the others; keep this isolation when extending. The tray is a thin GUI client that talks to the MCP server's plain-REST `/tray/*` surface.

Notes that the project layout doesn't tell you:

- **Mailvec.Indexer** does *not* call Ollama.
- **Mailvec.Mcp** — AspNetCore app exposing MCP tools over HTTP on `Mcp:BindAddress` (`127.0.0.1:3333` locally; `0.0.0.0:3333` in the container, where the Cloudflare tunnel is the only ingress and Access is the auth gate — see `docs/security.md`). Read-only against the database (except `view_attachment` and `get_attachment_page_image`, which read `.eml` files out of the Maildir). Also serves plain-REST `/tray/*` endpoints for the tray app plus `/health` and `/up` for monitors. In the container: **`/up`** is the forwarded monitoring endpoint (booleans only — the Uptime Kuma probe); **`/health`** is its detailed sibling and is served to **loopback callers only** (`Mcp:RestrictHealthToLoopback`, default true) because it discloses the archive path, corpus counts, model identity and the internal Ollama LAN address; `/tray/*` is **disabled entirely** (`Mcp:EnableTrayEndpoints=false`, baked into the image) *and* 404'd at the tunnel — it returns mail content and has no container consumer. Origin authentication of the Cloudflare Access assertion is available but off by default (`Mcp:Access`). See `docs/security.md`.
- **Mailvec.Cli** — admin commands hitting the same DB (including the `eval` / `eval-add` / `eval-import` family for retrieval-quality benchmarking).
- **Mailvec.Tray** — SwiftUI menu-bar app (macOS 14+). Polls `/tray/status` every 5s; never touches the SQLite database directly. See [`docs/contributing/tray.md`](docs/contributing/tray.md).

## Configuration

Each runnable service has its own `appsettings.json` containing only the sections it needs. Configuration POCOs live in `Mailvec.Core/Options/` and are bound in each service's `Program.cs`. Local overrides go in `appsettings.Local.json` (gitignored) — but note the **shared file wins over it** (it's inserted after all appsettings sources), so for the four shared keys below a per-binary Local file is silently ignored; use an env var (highest precedence) for one-off overrides of those. Publish never copies the Local file (`CopyToPublishDirectory=Never`).

**Single source of truth for user-specific settings** lives at `~/Library/Application Support/Mailvec/appsettings.Local.json`, written by `ops/install.sh` and read by every Mailvec binary via `SharedConfig.AddMailvecSharedConfig()` ([SharedConfig.cs](src/Mailvec.Core/Options/SharedConfig.cs)). Holds four of the five settings that used to be duplicated across the launchd plist's `EnvironmentVariables` and the MCPB manifest's `user_config`: `Archive:DatabasePath`, `Ingest:MaildirRoot`, `Ollama:BaseUrl`, `Fastmail:AccountId` (the fifth, `Mcp:LogToolCalls`, stayed env-var-only — see below). **Precedence**: per-binary appsettings → shared file → env vars (highest). Env-var wins means the MCPB bundle's `Mcp__LogToolCalls` (passed in by Claude Desktop's user_config UI) still overrides, and a developer can one-off `Ingest__MaildirRoot=...` in their shell for testing without editing the file.

`ArchiveOptions` (`DatabasePath`, `SqliteVecExtensionPath`) is bound by all four executables (consumed by `ConnectionFactory`). `IngestOptions` (`MaildirRoot`) is bound by the Indexer (scans the Maildir), the CLI (prints the path in `mailvec status`), the MCP server (`view_attachment` reads attachment bytes out of Maildir source files), and — as of the scanned-PDF OCR feature — the **Embedder** (its OCR pass reads `.eml` bytes via `MaildirAttachmentReader` to render scanned PDFs). The Embedder *used* to be the only executable that never touched the filesystem; OCR changed that. The bytes-decode logic is shared: `MaildirAttachmentReader` owns the containment-guarded read, and `AttachmentExtractor` (MCP) delegates to it.

Both indexer and CLI read environment variables with no prefix, so `Ingest__MaildirRoot=/path` works for either. The CLI looks for `appsettings.json` in `AppContext.BaseDirectory`, not the current working directory.

## sqlite-vec

Fetched as a prebuilt loadable (`vec0.dylib` / `vec0.so`) by `ops/fetch-sqlite-vec.sh` and loaded at runtime via `Microsoft.Data.Sqlite`'s extension-loading API. Path comes from `Archive:SqliteVecExtensionPath`. Fetch script supports `osx-arm64`, `linux-x64`, and `linux-arm64` (RID auto-detected, or passed as the first arg — the Dockerfile does this from `TARGETARCH`); add other RIDs there if needed. **Don't switch to the NuGet wrapper** — see `ops/UPGRADING.md`.

## Schema & data invariants

`schema/001_initial.sql` is the full schema (v9 baseline). These invariants are enforced at runtime and silent-corruption-prone if bypassed.

- **`messages.attachment_text` is a denormalized space-join of `attachments.extracted_text`** (any attachment with non-empty text — i.e. status `done` or `ocr`), built by `MessageRepository.BuildAttachmentText` and written in the same transaction as `attachment_names`. It feeds the 6th `messages_fts` column so keyword search hits attachment bodies; if a write path updates `attachments.extracted_text` without rebuilding `messages.attachment_text`, FTS silently drifts and dual-signal RRF fusion stops boosting documents that should match both the BM25 and vector legs.
- **The embedding model is part of the schema.** `chunk_embeddings` declares a fixed dimension — substituted from `Ollama:EmbeddingModel`/`EmbeddingDimensions` on fresh-DB creation by `SchemaMigrator.SubstituteEmbeddingConfig` (each substitution token must appear exactly once in `001_initial.sql`; the migrator throws otherwise). `OllamaClient` validates returned vector lengths against `Ollama:EmbeddingDimensions` and L2-normalizes any unnormalized vector (vec0 KNN is L2; unit norm is what makes it rank like cosine); `EmbeddingWorker` refuses to start if `metadata.embedding_model` disagrees with config. **`mailvec switch-model` is the only sanctioned way to change an existing DB's model** — it rebuilds the vec0 table at the new dimension, clears chunks, re-queues every message, and updates metadata in one transaction (see `docs/contributing/embedding-experiments.md`). **Never bypass these checks** — mixing vector spaces silently corrupts similarity scores in ways that look plausible. The embedding seam is `IEmbeddingClient` (`Mailvec.Core/Embedding/`); `OllamaClient` is the sole implementation, and all consumers + DI registrations go through the interface.
- **FTS5 sync is trigger-driven.** `messages_ai`/`messages_ad`/`messages_au` keep `messages_fts` in lockstep with `messages`. Don't bypass the triggers with raw inserts into `messages_fts`.
- **`vec0` must load before the schema applies**, because `001_initial.sql` declares `chunk_embeddings` as a `vec0(...)` virtual table. `ConnectionFactory` loads the extension on every `Open()`. The native library is copied into each project's `bin/.../runtimes/<rid>/native/` by `Directory.Build.props` (a `runtimes/**` glob that no-ops when the fetch script hasn't run).
- **`chunk_embeddings` has no foreign key to `chunks`** because vec0 virtual tables don't support FKs. `ChunkRepository.DeleteChunks` deletes from both tables explicitly inside one transaction. Don't `DELETE FROM chunks` directly without also cleaning `chunk_embeddings`.
- **Vector serialization to sqlite-vec.** `FLOAT[N]` columns are stored as packed little-endian float32 bytes. `VectorBlob.Serialize/Deserialize` in `ChunkRepository.cs` is the only place that does this conversion — keep all sqlite-vec writes/reads going through it.
- **`PRAGMA journal_mode = WAL` must be applied via `ExecuteScalar`, not `ExecuteNonQuery`.** Microsoft.Data.Sqlite silently no-ops result-returning pragmas under `ExecuteNonQuery`, so the WAL pragma in `001_initial.sql` was *not actually setting WAL mode* — DBs were running in plain rollback-journal `delete` mode. Confirmed by reading header bytes 18-19 (`01 01` for journal, `02 02` for WAL). Fix lives in `ConnectionFactory.Open()`: a per-connection `PRAGMA journal_mode = WAL;` via `ExecuteScalar`, idempotent and self-healing for any DB created before the fix landed. Don't move this back into the migration script.
- **`Microsoft.Data.Sqlite.ExecuteNonQuery` silently stops at the first `CREATE TRIGGER ... BEGIN ... END;`.** The internal trigger semicolons confuse its statement iterator. `SqlScriptSplitter` tokenises scripts itself (BEGIN/END depth-tracking) and executes one statement at a time. Don't go back to `ExecuteNonQuery`-on-the-whole-script.

Attachment text:

- **`attachments.extracted_text` / `extracted_at` / `extraction_status`** hold the recovered plain text. `chunks.source` ('body' | 'attachment') + `chunks.attachment_id` let search results trace back to a specific document.
- **`extraction_status` is a stable enum** declared as constants on `AttachmentTextExtractor`: `done`, `ocr`, `no_text`, `unsupported`, `oversize`, `encrypted`, `failed`. Persist these values verbatim — they're surfaced through `get_email`'s `AttachmentInfo.ExtractionStatus` so Claude can tell the user "I couldn't read this PDF because it was encrypted". **`ocr`** means a scanned PDF stuck at `no_text` was later recovered by the **embedder's** vision-model OCR pass (written by `MessageRepository.SaveOcrText`, not the indexer); it's treated as searchable like `done` (both the FTS `attachment_text` rebuild and `get_email`'s `IndexedForSearch` include it). The embedder OCRs anything at `no_text` that's a PDF, so a re-index that resets a doc to `no_text` self-heals on the next OCR pass. See `docs/contributing/attachment-ocr.md`.
- **An attachment id does not identify a document — every OCR write-back is identity-guarded.** `attachments.id` is an `INTEGER PRIMARY KEY` *without* `AUTOINCREMENT`, so a row deleted from the tail of the rowid space hands its id to the next insert, possibly one belonging to a different message. The OCR pass selects a candidate and writes back minutes later (file read + page renders + vision calls in between), and a status-only guard can't tell "still my document" from "a different pending scan that inherited this rowid" — a freshly parsed scanned PDF lands at exactly `no_text` (an image at `unsupported`). `SaveOcrText` / `MarkAttachmentOcrFailed` / `MarkAttachmentImageNoText` therefore all take the whole `OcrCandidate` and match `MessageRepository.OcrIdentityMatch`: same id, same `message_id`, same `part_index`, and the parent's `content_hash` unmoved (it covers the multipart structure, so it's what decides whether the bytes at that part are still the document we OCR'd; `IS`, not `=`, so legacy NULL hashes match). **Pass the candidate through — never just the id.** A skipped write is always safe: the replacement row is re-selected next cycle against its own snapshot. **The same identity rule applies to the in-memory failure counters, and to what a guarded write reports.** `AttachmentOcrService._visionFailures` keys on `(attachment_id, message_id, part_index, parent content_hash)`, not the id — keyed by id, a replacement document inherited the previous occupant's strikes and could retire to `failed` on its first vision error. And `SaveOcrText` / `MarkAttachmentOcrFailed` / `MarkAttachmentImageNoText` return `OcrWriteOutcome` (`Committed` / `Stale`) rather than void: a skipped write used to be indistinguishable from a committed one, so the pass counted `done`, cleared strikes, logged success, and told the worker OCR had produced work (an immediate extra poll for nothing). **Count committed transitions only.** Tests: `MessageRepositoryOcrTests.SaveOcrText_reports_Stale_when_the_guard_matches_nothing`, `AttachmentOcrServiceTests.Strikes_do_not_carry_across_a_document_change_on_the_same_row`. Getting this wrong marks a document searchable under text it doesn't contain, with `attachment_text` rebuilt for the *snapshot's* parent rather than the row's current one (the FTS drift the denormalization invariant above exists to prevent), and nothing left to re-trigger. Tests: `MessageRepositoryOcrTests.SaveOcrText_does_not_write_onto_a_row_id_reused_by_another_message` / `..._after_the_parent_content_changed`.
- **The same snapshot rule applies to `mailvec extract-attachments`, and it runs in three stages for a second reason.** Parsing AND extraction both happen *outside* the write transaction (stage 1 parse, stage 2 read the candidate set, stage 3 extract with no connection open, stage 4 revalidate + apply). Not tidiness: `BeginTransaction()` issues `BEGIN IMMEDIATE`, so a transaction opened around the extract loop holds SQLite's single writer slot across every MIME decode and PdfPig/OpenXml parse, stalling the indexer, embedder, OCR write-back, maintenance commands and MCP startup migration for as long as the document takes. It used to do exactly that while carrying a comment claiming otherwise — **if you need a value from the database mid-extraction, fetch it in stage 2, never inside the tx.** Pinned by `ExtractAttachmentsCommandTests.Extraction_runs_with_the_writer_lock_free`, which probes for the lock from inside the extractor. The out-of-transaction parse is also what leaves a window for a concurrent indexer re-parse to leave it holding a parse of a file the row no longer points at — and its results are mapped onto rows by `part_index`. `ExtractAttachmentsCommand.MessageSnapshotUnchanged` re-checks the message's `content_hash` + Maildir location inside the transaction and commits nothing on a mismatch (reported in the run summary, never silently). Default mode is additionally self-guarding — its candidate predicate is `extraction_status IS NULL` and the indexer always writes a non-null status — so the reachable exposure is the `--reextract-*` modes, whose predicates match on content-type/filename regardless of status. `backfill-inline-images` needs no equivalent: `AddInlineAttachments` is `INSERT OR IGNORE` against `UNIQUE(message_id, part_index)`, so a race degrades to a skipped insert.
- **A missing Maildir source is STALE, never `failed`.** `extract-attachments` reports and skips a message whose `.eml` isn't at the recorded path, leaving its attachments at `extraction_status IS NULL` for a later run. It used to stamp them `failed` to avoid revisiting the message; that was silent data loss on an ordinary mbsync rename — the path vanishes while the bytes live on unchanged at the new path, the unchanged content means `Upsert` never calls `ReplaceAttachments` (so the stamps survive the rescan), and the default candidate predicate is `extraction_status IS NULL` (so nothing revisits them). Permanently unsearchable, no error, nothing left to re-trigger extraction. Re-attempting a genuinely-deleted message costs one `File.Exists` per run, which is the right trade; the run summary reports the count so a bounded run can't read as full coverage. Tests: `ExtractAttachmentsCommandTests.Missing_eml_file_leaves_attachments_untouched_for_a_later_run` / `A_second_run_after_the_source_reappears_extracts_normally`.
- **Office formats are ZIP containers, so `Indexer:AttachmentMaxBytes` is not a bound on the parse.** DOCX/XLSX/PPTX are opened through `AttachmentTextExtractor.OfficeOpenSettings`, which sets `MaxCharactersInPart` — **never 0, the SDK's "unlimited"**. Measured before it existed: a **0.95 MB** DOCX allocated **2.45 GB** and took 9.1 s, past the indexer's 2 GB container limit at 1/26th of the 25 MB input ceiling; with the setting it throws in 0.4 s having allocated 66 MB. `MaxExtractedTextChars` is *not* protection here and reading it as such is the trap — the break fires only after the whole part DOM is materialized, so the code looks bounded while allocating without limit. The consequence is a wedge, not a crash: extraction runs inside the scan before any row is written, so an OOM-kill commits nothing, `restart: unless-stopped` brings the indexer back, and it parses the same attachment forever — all indexing stopped, by anyone who can send the user mail. Tests: `OfficePartLimitTests` (a valid small package AND a bomb per format, so a malformed-package false pass is impossible).
- **OCR candidate selection needs a cursor; the read backoff is not a fairness guarantee.** `AttachmentOcrService` sweeps the id space from `_pdfCursor`/`_imageCursor` because both candidate queries are `ORDER BY a.id LIMIT` and a failed byte read leaves the row's status untouched — so selecting from the lowest id every cycle re-picks the same head forever. `_readBackoffUntilCycle` only raises the threshold: with batch `N` and backoff `K` it clears `N × K` blockers in `K` cycles, at which point the first is selectable again (20 at the defaults, ~10 with both passes sharing `_cycle`). The cursor must advance past rows attempted *and* skipped-for-backoff, but **not** past rows the over-fetch returned and the scan never examined. Also: a poison document now retires after `MaxVisionAttempts` **sweeps**, not cycles — no test here may assume selection order. See [`docs/contributing/attachment-ocr.md`](docs/contributing/attachment-ocr.md).
- **Extraction libraries are pure-managed.** PDF via `PdfPig` (Apache 2.0); DOCX / XLSX / PPTX via `DocumentFormat.OpenXml` (MIT); iCalendar (`.ics`) and vCard (`.vcf`) via hand-rolled unfold/field extractors; plain text decoded via the declared MIME charset first (strict), then UTF-8, then Windows-1252 — see the charset-ladder note in `docs/contributing/attachment-indexing.md`; the pre-fix mojibake backfill is `mailvec extract-attachments --reextract-text`. No native deps, no shell-out, no OCR. The full supported-format list plus every size/dimension/filetype skip gate and its rationale live in [`docs/contributing/attachment-indexing.md`](docs/contributing/attachment-indexing.md). Scanned PDFs come back as `extraction_status='no_text'` and are intentionally not retried. **This applies to the indexer's text-extraction path only** — and "no OCR" is no longer absolute: the **embedder** OCRs scanned PDFs out of band (see "scanned-PDF OCR" below). PDF page rasterisation lives in **`Mailvec.Pdf`** (`PdfRenderer`, via `PDFtoImage` = PDFium + SkiaSharp, **native**) — the only native dep in the read path besides `sqlite-vec`, referenced **only** by `Mailvec.Mcp` (`get_attachment_page_image`) and `Mailvec.Embedder` (the OCR pass), keeping it out of Core/Indexer/Cli. Platform-gated with `[SupportedOSPlatform]` to macOS/Linux/Windows; native assets for `osx-arm64`/`osx-x64`/`linux-x64`/`linux-arm64` come transitively through NuGet (no fetch script, unlike `vec0.dylib`) and bloat the self-contained MCPB bundle. The renderer caps the long edge at 1536px (downscale-only) and encodes JPEG q85 on a white background — a fixed-DPI PNG let a large-MediaBox scan balloon to ~20MB, pointless since Claude downsamples to ~1568px anyway. `Mailvec.Pdf` also holds `ImageRenderer`, which normalises **image attachments** for the same OCR pass: SkiaSharp decodes JPEG/PNG/etc., but its native build ships no TIFF codec, so TIFF is decoded via the pure-managed `BitMiracle.LibTiff.NET` (magic-byte routed, no native dep — works on the Linux target). HEIC stays unsupported (would need native libheif) and returns null → `failed`.

- **Scanned-PDF OCR (the embedder).** Image-only PDFs land at `extraction_status='no_text'` from the indexer (pure-managed PdfPig can't read them). The embedder's OCR pass (`AttachmentOcrService`, behind `Embedder:OcrEnabled`, default on) then renders each page (`PdfRenderer`) and transcribes it with a local Ollama **vision** model (`Ollama:VisionModel`, default `qwen2.5vl:7b`) via `IVisionClient`/`OllamaVisionClient`, writes the text back as `status='ocr'`, and re-queues the message so it's embedded + FTS-indexed. Runs *before* the embed pass each cycle. The vision model is **not** pinned (loads on demand, `Ollama:VisionKeepAlive` empty → Ollama's default), so it and the embedding model never need to coexist in RAM. Degrades gracefully: if the model isn't pulled it logs + skips (leaves `no_text`); `mailvec doctor` warns. Full design + rationale in `docs/contributing/attachment-ocr.md`.

## Service liveness (heartbeats)

Containers removed the answer to "is the indexer running?" — there's no `launchctl` in compose, and the MCP server can't see a sibling container's state without mounting the Docker socket. Liveness therefore travels through shared state, like everything else here. Source: [`ServiceHeartbeat.cs`](src/Mailvec.Core/Health/ServiceHeartbeat.cs).

- **Three signals, three different questions — don't collapse them.** `heartbeat.<svc>.at` (liveness: the process exists, written by `HeartbeatService` on its **own timer**); `heartbeat.<svc>.cycle_at` (progress: the work loop turned, written by the worker); `EmbedderHealthKeys.*` (batch outcome: the embedder is draining its backlog). Each is the only answer to its question — the batch-outcome keys are deliberately *not* written on an idle cycle, so an idle embedder and a dead one are identical through them; that's why liveness is separate.
- **The liveness beat must never be emitted from the work loop.** One Ollama batch or one OCR page render routinely outlives the embedder's 30 s poll interval, so a beat-on-cycle-completion design reports a *busy* worker as dead. That's why `HeartbeatService` is a separate `BackgroundService` with its own `PeriodicTimer` — the decoupling is the design, not an accident of structure.
- **Every writer declares its own cadence** (`interval_s`) alongside the beat, and the reader judges staleness at `StaleAfterMissedBeats` × that. The MCP server binds neither `IndexerOptions` nor `EmbedderOptions`, so the alternative was config coupling that silently desyncs the moment someone retunes a cadence on one side only.
- **Unknown ≠ stale.** No beat on record (fresh DB, worker hasn't beaten yet) reports `Known=false`, never `Stale=true`. A false red on first boot teaches the user to ignore the indicator.
- **`HeartbeatService` calls `EnsureUpToDate()` before its first beat.** `BackgroundService` does *not* guarantee `ExecuteAsync` has run when `StartAsync` returns, and the indexer's worker yields before migrating — so on a fresh DB the first beat hit `no such table: metadata`, got swallowed by the best-effort catch, and left a *running* service reading unknown for a full interval. Concurrent migration is safe by design (`BEGIN IMMEDIATE`; the loser re-reads inside the lock). Test: `HeartbeatService_beats_against_an_unmigrated_database`.
- **mbsync is file-backed, not metadata-backed** — it's a POSIX-sh sidecar with no SQLite. It writes `<maildir-parent>/.mailvec-mbsync-heartbeat` (ISO time + interval, `.tmp`-then-`mv`), read by `MbsyncHeartbeatFile`. **The beat sits beside the Maildir root, never inside it**: `MaildirScanner` walks the root and Maildir++ names folders with a leading dot, so a dotfile in the tree risks being parsed as a folder. Moving `Ingest:MaildirRoot` to the mount point itself breaks this.
- **The MCP server has no heartbeat, deliberately.** It's read-only against the DB, and anything reading a heartbeat is by definition talking to a live MCP server.
- **`heartbeat.<svc>.instance` detects a duplicate worker; it must never prevent one.** Nothing serializes two indexers against one database and Maildir — `MessageIngestService`'s coalescing channel is process-local — and two overlapping scans can soft-delete live messages (each stamps every seen file's `sync_state.last_seen_at` to its own start time, then reconciles deletions against it). Both processes write this one key, so a `HeartbeatService` reading back an id that isn't its own knows another is beating; it logs and stamps `heartbeat.<svc>.duplicate_seen_at`, which `ServiceHeartbeat.Read` surfaces as `ServiceLiveness.DuplicateInstanceSeen` on a freshness window, so it self-clears when the duplicate stops. **Two consecutive sightings are required** — an ordinary restart finds the previous run's id in the slot, and reporting on one sighting would fire on every container restart. **Do not escalate this to refuse-to-start**: a container restarting under `restart: unless-stopped` returns while the old beat is still fresh and would refuse to boot, turning the diagnostic into the wedge it warns about. Exclusion (a real interprocess lock around `ScanAll`) was considered and deferred — see `docs/future-ideas.md`.
- **Liveness never flips `/health`'s 503.** `/health` is the mcp container's own compose healthcheck; folding a sibling's death into `Status` would mark *MCP* unhealthy because the *indexer* died — wrong, and actively misleading when triaging. Liveness rides in `HealthReport.Services` for clients to render.

## Indexing & change detection

- **Content-change detection lives in `MessageRepository.Upsert`.** Each parsed message carries a SHA-256 of its body section (computed by `MessageBodyHasher.Hash` over `MimeMessage.Body.WriteTo` — explicitly excludes the top-level header block so post-delivery rewrites like DKIM-Verified don't trigger spurious re-embeds). On upsert we compare against stored `messages.content_hash` in the same transaction and return `UpsertOutcome { Id, ContentChanged }`. Keying off Message-ID (not Maildir path) avoids false positives from renames; hashing `MimeMessage.Body` bytes (not `parsed.BodyText`) decouples from HTML-converter changes — those are handled separately by `mailvec rebuild-bodies --reembed`. Legacy NULL hashes are treated as "not changed" so the migration doesn't mass-clear.
- **Re-queue on content change is atomic with the body write.** The `Upsert` transaction that writes the new `body_text`/`content_hash`/FTS **also** sets `embedded_at = NULL` (gated on the same `$attachments_reset` flag as the attachment refresh, so a no-op rescan leaves it alone). The scanner ([`MaildirScanner.TryIngest`](src/Mailvec.Indexer/Services/MaildirScanner.cs)) still calls `ChunkRepository.ClearEmbeddingsForMessage(id)` when `ContentChanged == true`, but only to drop the stale chunks/vectors promptly — it is no longer load-bearing for correctness. **Don't move the `embedded_at` clear back out of the `Upsert` transaction**: if a crash or `SQLITE_BUSY` lands between the body write and a separate clear, the row keeps a stamped `embedded_at` whose `content_hash` now matches the new body, so no later rescan detects a change and old vectors silently shadow new FTS text forever. Tests: `MessageRepositoryTests.Upsert_clears_embedded_at_atomically_on_content_change` / `Upsert_preserves_embedded_at_on_noop_rescan`.
- **The embedder guards its write against a mid-embed content change.** `EmbeddingWorker` snapshots each message's `content_hash` **and `embed_epoch`** in `EnumerateUnembedded`, spends seconds-to-minutes in Ollama, then passes both to `ChunkRepository.ReplaceChunksForMessage(..., expectedContentHash, checkContentHash: true, expectedEmbedEpoch)`. The write re-reads both inside its (BEGIN IMMEDIATE) transaction and abandons everything — nothing committed — if the row is gone or either value moved. Without this, the indexer committing a body change during the embed call (which reset `embedded_at` and bumped `content_hash`) would be clobbered by stale-body vectors + a fresh `embedded_at` stamp, with no hash delta to ever re-trigger — the same silent divergence from the other side. Skipped messages stay `embedded_at IS NULL` and re-embed against the new body next poll. Test: `ChunkRepositoryTests.ReplaceChunksForMessage_skips_and_preserves_state_when_content_hash_changed`.
- **`messages.embed_epoch` (v7) is the re-queue counter that catches what `content_hash` can't.** Several writers clear `embedded_at` *without* changing `content_hash` — `extract-attachments` (re-embed is its default; `--no-reembed` opts out), `backfill-inline-images`, the OCR write-back (`SaveOcrText`), `rebuild-bodies --reembed`, `reindex`, `switch-model` — so the hash guard alone would let an in-flight embed stamp right over the re-queue: new attachment text keyword-searchable but never vector-embedded, permanently, with nothing to re-trigger. **Every write path that clears `embedded_at` must bump `embed_epoch` in the same transaction — and must clear it in the same transaction that writes the content that made it stale.** `extract-attachments` and `rebuild-bodies --reembed` both used to re-queue in a *later* transaction, which for `extract-attachments` was permanent: its default candidate predicate is `extraction_status IS NULL`, and the committed text write makes that non-null, so a failure in between left new attachment text in FTS beside pre-extraction vectors that no re-run would ever re-select. Both now re-queue inline; their bulk `ClearEmbeddings*` calls are prompt stale-vector cleanup only, not load-bearing (same split as `MaildirScanner.TryIngest`). The rule again, because it is the one that gets forgotten: **bump `embed_epoch` in the same transaction**; the guarded chunk write skips when the epoch moved. If you add a new re-queue path, bump the epoch there too. **The embedder's quarantine and strike maps key on that same snapshot** — `(message_id, content_hash, embed_epoch)`, not the id. A message id is an address, not an identity: keyed by id alone, strikes carried across an edit and a quarantine outlived the content that earned it, so editing an unembeddable message (the obvious remedy) silently did nothing until a process restart — while the code comment claimed otherwise. `EmbeddingWorker.PruneQuarantine` reconciles against the live rows before each enumeration and releases anything whose snapshot moved. Test: `EmbeddingWorkerTests.Quarantine_is_released_when_the_message_content_changes`. Test: `ChunkRepositoryTests.ReplaceChunksForMessage_skips_when_embed_epoch_moved`.
- **`sync_state.folder` (v8) is the folder-membership source for search.** A message can live in several folders at once (Gmail's All Mail + every label, Fastmail multi-label, self-CC'd INBOX + Sent) but `messages` keys on `message_id UNIQUE`, so `messages.folder` holds only the attributed primary copy. The folder search filter (`SearchFilterSql.Append`) matches `m.folder OR EXISTS(sync_state)`, and `FolderStats`/`list_folders` count from membership (with a legacy fallback while the column is unpopulated). **Every `SyncStateRepository.Upsert` call must pass the copy's folder** — the parameter has no default on purpose; writing NULL silently shrinks membership and folder filters stop matching that copy.
- **Folder attribution is first-seen-wins, not last-writer.** `MessageRepository.Upsert`'s conflict clause preserves the stored `(folder, maildir_path, maildir_filename)` triple as a unit while the row is live — taking `excluded` made the attributed folder whichever duplicate copy the scan parsed last, flapping between scans. Genuine moves are handled by the scanner's rename-repair pass at the end of the same scan (the stale old path + fresh Message-ID triggers `UpdateMaildirLocation`), which is therefore **load-bearing** — don't remove it. The one exception is resurrection: a soft-deleted row's stored path is exactly the vanished file and its sync_state rows are gone (no repair will ever fire), so on `deleted_at IS NOT NULL` the conflict clause takes the new copy's triple.
- **Content follows attribution: an `Upsert` from a non-attributed copy is a no-op.** Duplicate copies of one Message-ID are not always byte-identical (a mailing-list copy carries an appended footer its Sent counterpart doesn't), so accepting body/attachment content from whichever copy parsed last left the row holding copy A's *location* and copy B's *bytes* — and `view_attachment` / the OCR pass, which resolve `part_index` against the attributed `.eml`, then read a document the metadata never described. It also made `content_hash` alternate between copies, so every rescan that re-parsed both looked like a body change and burned a full re-embed. `Upsert` therefore returns the existing id untouched when the incoming `(maildir_path, maildir_filename)` isn't the stored one (soft-deleted rows exempt — resurrection re-points location *and* content). **Because of this, the rename-repair pass must also call `SyncStateRepository.ClearContentHash` on the survivor's path**: repointing moves attribution but not content, and without forcing a re-parse the survivor rides the mtime fast path forever and the row never re-aligns — that also covers a rename whose file content changed, which would otherwise be recorded in sync_state and never applied. Costs one re-parse per repoint. **The repoint and the hash clear must commit in ONE transaction** (`UpdateMaildirLocation`'s connection+transaction overload): as two autocommit writes, a crash or `SQLITE_BUSY` between them left the row pointing at the new path while holding the vanished copy's content — permanently, because the survivor kept a non-null hash (so the mtime fast path skipped it) and the repair pass skips any row already pointing somewhere live. Nothing could detect or repair it. A failure now leaves the stale `sync_state` entry intact (it's removed only after the repair loop), so the next scan retries. Tests: `MessageRepositoryTests.Repoint_and_hash_clear_roll_back_together` / `..._commit_together`, `MessageRepositoryTests.Upsert_from_a_copy_at_another_path_does_not_rewrite_the_attributed_row`, `MaildirScannerTests.Divergent_duplicate_copies_*` / `Repointing_to_a_divergent_survivor_realigns_the_stored_content`.
- **Rename detection.** When mbsync renames `new/foo` → `cur/foo:2,S` between scans, the same Message-ID appears at a fresh path while the old `sync_state` row still references the old path. The scanner uses `SyncStateRepository.FreshMessageIds(since)` to exclude renamed messages from the soft-delete pass.
- **Scans must never overlap.** `MessageIngestService` drives scans from two triggers (the watcher pulse and the periodic timer) but funnels both through a coalescing single-slot channel with a single consumer, so `MaildirScanner.ScanAll` runs one-at-a-time. This is a correctness invariant, not just a perf one: each scan stamps every seen file's `sync_state.last_seen_at` to its own start time (last-writer-wins) and reconciles deletions with `StaleEntries(olderThan: scanStart)`. If a slower *older* scan overwrites a file's `last_seen_at` after a newer scan already recorded it, the newer scan's reconciliation sees the live file as stale (`last_seen_at < its scanStart`, and its Message-ID absent from `FreshMessageIds(scanStart)`) and soft-deletes it — then `purge-deleted` in that window would hard-delete the row + chunks + vectors. **Don't reintroduce a second concurrent `ScanAll` caller** (e.g. calling it directly from the pulse handler again). `ScanAll` itself stays a synchronous, non-reentrancy-guarded primitive so tests can call it directly; the serialization lives in the driver.
- **The scanner's fast path compares RECORDED file identity, not scan time.** At the top of [`MaildirScanner.TryIngest`](src/Mailvec.Indexer/Services/MaildirScanner.cs): if `sync_state` remembers this exact path AND the file's current mtime + size **equal** the `file_mtime_utc` / `file_size` recorded at the last ingest (v9), the scan refreshes `last_seen_at` and returns without re-parsing. Without the fast path, every periodic rescan would re-extract every PDF in the archive — the dominant cost on a real corpus. **The equality is the point.** It used to be `File.GetLastWriteTimeUtc(file) <= prior.LastSeenAt`, and `last_seen_at` is when Mailvec *looked*, not what it *saw*: any file whose content changed while its mtime stayed at or below the previous scan's start satisfied that test, and since each scan then re-stamped `last_seen_at` later without parsing, the skip self-perpetuated — body text, attachments, FTS and vectors pinned forever to content no longer on disk, silently. mbsync can't produce that shape (new files carry current times; flag changes are renames, which land at a fresh path and miss the path-keyed lookup), but every restore tool can — `rsync -a`, `cp -p` and `tar -x` all preserve mtime by design. **Don't relax this back to a comparison against scan time.** A NULL identity (pre-v9 rows) falls back to the old comparison for exactly one scan while recording the real identity, so live rows converge after one full scan with no mass re-parse. Known residual: a replacement keeping both mtime and byte count is still skipped — only hashing would catch it, and hashing every file every scan is the cost this path exists to avoid. `ContentHash` must also be non-null: a NULL hash is the "last ingest failed" retry marker. Tests: [`MaildirScannerTests.Rescan_skips_unchanged_files_via_mtime_fast_path`](tests/Mailvec.Indexer.Tests/MaildirScannerTests.cs) / `Rescan_reparses_a_file_whose_content_changed_under_a_restored_mtime`.
- **Attachment rows are NOT replaced on no-op rescans.** `MessageRepository.Upsert` only calls `ReplaceAttachments` when `IsNewInsert || ContentChanged` (surfaced via `UpsertOutcome.AttachmentsReset`). Without this guard, the `extracted_text` column would be wiped and rebuilt on every scan even when the parent body hadn't changed. The body's `content_hash` covers the multipart structure, so any real attachment delta forces a hash change → reset → re-extraction.
- **Extraction runs inside the indexer's parser.** `MessageParser` takes an optional `AttachmentTextExtractor` ctor dep; the production DI graph in `Mailvec.Indexer/Program.cs` wires it in, while the parameterless ctor (used by tests / the MCP `view_attachment` flow) skips extraction and produces metadata-only attachments. Keep this split — extraction is the only Maildir-touching step that the embedder and MCP server should never invoke.
- **`AttachmentMaxBytes` (default 25MB) is the per-attachment extraction cap.** Anything larger gets `extraction_status='oversize'` and is skipped without decoding. Don't drop this much — a 200MB image-heavy PDF can exhaust RAM during PdfPig parse. Caller declared sizes are checked first (cheap pre-filter), then bytes are re-checked after MIME decode to catch under-reported sizes.
- **`part_index` maps to a MIME part via `MessageParts.Indexable(mime)` — the single source of truth shared by the writer (`MessageParser`) and the reader (`MaildirAttachmentReader`, hence MCP `view_attachment` + the OCR pass).** The set is `mime.Attachments` (disposition=attachment) **first**, then inline image parts (MimeKit's `Attachments` excludes `Content-Disposition: inline` / `cid:` images — commonly real content: photographed docs pasted inline by Apple Mail, forwarded post images). **Inline images are appended after the attachments, not interleaved**, so existing rows' `part_index` never shifts — capturing them is an additive backfill (`mailvec backfill-inline-images`), not a reindex. If the two enumerations ever diverge, `view_attachment`/OCR silently read the wrong bytes for a part. Inline images extract to `unsupported`, so the embedder's image-OCR pass picks them up under its gate. The backfill's candidate set is `body_html LIKE '%cid:%'` (bounded; the inline-ref pattern) — it misses inline images in HTML-less mail, a rare edge.
- **The attachment read carries a per-caller size ceiling, and `maxBytes` has NO default anywhere on that path.** `MaildirAttachmentReader.Read`/`ReadBytes` and `AttachmentExtractor.ExtractInMemory` all require it, because the right answer differs per caller and a default silently hands one caller's policy to the next one added: `Extract` (tray Save, `mailvec extract-attachments`) passes **null** — a user who asked for the file asked for all of it; the MCP viewers pass `Mcp:AttachmentInlineMaxBytes`; the OCR passes pass `Embedder:OcrMaxAttachmentBytes` (both 25 MB, matching `Indexer:AttachmentMaxBytes`, so a document too big to extract text from is also one we won't inline or OCR). **Enforced DURING the decode** via a bounded write stream, never by pre-checking a size: `Content-Length` and `attachments.size_bytes` are claims about the part, and a cap that trusts a claim isn't a cap. Over it, `AttachmentTooLargeException` — terminal for that document, not something to retry.
- **A path that skips the Maildir read must still call `MaildirAttachmentReader.EnsureSourceExists`.** `view_attachment` answers summary-only types (PDF, DOCX, zip) from the `attachments` row without opening the `.eml` — the bytes were decoded in full and discarded, the largest allocation in the tool. But the read it skips is also what answers "is the `.eml` still there?" and what runs the symlink containment guard (both live in the path resolve), so skipping it wholesale returned a confident summary for a message whose file had vanished and quietly retired the disclosure-controlled `FileNotFoundException` the MCP tools translate for the client. One `stat()` buys both back. Same rule for any future fast path here. The short-circuit must also resolve name/type through `AttachmentExtractor.ResolveFileName`/`ResolveContentType` rather than the raw columns (mailers send photos as `application/octet-stream`; reading the column classifies a JPEG as un-inlineable binary and silently stops showing images), and must decline to decide — falling through to the read — on no matching row, unknown size, image, or text-like. Full rationale + tests: [`docs/contributing/attachments.md`](docs/contributing/attachments.md).

## HTML parsing

- **HTML body parsing uses AngleSharp, not MimeKit.** The design doc's reference to MimeKit's `HtmlToText` was wrong (MimeKit doesn't ship that helper). We use AngleSharp's DOM via `Mailvec.Core.Parsing.HtmlToText`, which strips marketing-email noise (hidden preheader text, tracking pixels, image-only and unsubscribe/preferences links, `<address>` and `<footer>` blocks). Output runs through `TextNormalize` and `BoilerplateFilter`. **Tuning detail to remember:** `font-size:0`, `max-height:0`, and `max-width:0` on outer `<td>` wrappers are *layout hacks* (defeating inter-cell whitespace) where the real text lives in inner elements that override the property — never treat these as hide signals or you'll nuke whole branches of legitimate content. Migration when the converter changes: `mailvec rebuild-bodies --reembed` re-derives `body_text` from stored `body_html` and clears `embedded_at`.

## Embedding & chunking

- **Subject is prepended to body before embedding** in `EmbeddingWorker.BuildEmbeddingText`. Newsletters often have a meaningful subject and thin body; replies the other way.
- **Empty-body messages get a stamped `embedded_at` with zero chunks** so the worker doesn't loop on them forever. `ChunkRepository.ReplaceChunksForMessage` accepts empty lists for this reason.
- **Embedder stitches body + attachment chunks into a single per-message chunk stream.** `EmbeddingWorker.BuildChunksForMessage` emits body chunks first (so `chunk_index = 0` is always body when present), then per-attachment chunks tagged `source='attachment'` + `attachment_id=<id>`. `chunk_index` is renumbered sequentially across both sources to satisfy `UNIQUE(message_id, chunk_index)`. Attachment chunks include the filename as a prefix so a query matching the document name still ranks even if the filename token isn't repeated in the body.
- **Chunk size + two layers of overflow handling.** Default `ChunkSizeTokens=200` (chars/4 = 800 char ceiling). The 4-chars/token heuristic is unreliable on real email — punctuation, embedded URLs, base64, marketing-email HTML residue, and non-ASCII can push BPE token counts to 1-2 chars/token, exceeding `mxbai-embed-large`'s 512-token context. Two safety nets:
  1. **Server-side: Ollama's `truncate: true` flag** works for batched `/api/embed` as of Ollama **0.21.2** (this is the floor). The server logs `llm embedding error: the input length exceeds the context length` (INFO-level, not an error response), silently truncates, and returns HTTP 200. Verified empirically by `mailvec audit-embeddings`.
  2. **Client-side fallback in `OllamaClient.EmbedAsync` for HTTP 400**: oversize batches get split in half and recursed; a singleton that still doesn't fit is truncated by 50% repeatedly until it succeeds (down to a 64-char floor). Don't disable this without replacing it with a real tokenizer-based pre-check — it's the safety net if a future Ollama version regresses.

## Search

- **Search filters live on the search services in Core, not on the MCP tool.** `KeywordSearchService.Search`, `VectorSearchService.SearchAsync`, `HybridSearchService.SearchAsync`, and `MessageRepository.BrowseByFilters` all accept a `SearchFilters?` (`Folder` / `DateFrom` / `DateTo` / `FromContains` / `FromExact` / `HasAttachments` / `AttachmentType`). The shared `SearchFilterSql.Append` helper appends WHERE clauses and binds params so filter semantics stay identical across the BM25 leg, the vector leg, and the query-less browse path. Hybrid RRF fuses two ranked lists, so post-filtering only one side would skew scores. **Don't** post-filter in the MCP layer. `FromExact` takes precedence over `FromContains` when both are set. The `Folder` filter matches a message when **any** of its live copies is in the folder (`m.folder = $folder OR EXISTS` against `sync_state` membership) — not just the attributed `messages.folder`; a folder-filtered hit can therefore display a different folder than the filter, which is correct.
- **Vector KNN runs before the filter join.** `chunk_embeddings MATCH $vec AND k=$k` returns the raw nearest neighbours; the filter is applied in the joined CTE. With a restrictive filter, a small `k` leaves the post-filter set short even when good matches exist further down the KNN list (this once made bare `mode=semantic` + a folder filter return ~1 result). **`VectorSearchService.SearchByVector` is the single source of truth for the workaround**: it ALWAYS runs the escalation loop — even "unfiltered" KNN is post-filtered by `deleted_at IS NULL` (soft-deletes crowd the ranking until a manual purge) and by the one-row-per-message window — escalating `k` (×8 per round, starting at `max(k, limit)`, bounded by the chunk count) until it has `limit` post-filter hits or has fetched every chunk. Callers pass a base `k` and rely on the escalation loop for correctness; the semantic-mode callers (MCP `search_emails`, `TraySearchService`, the eval ranking source) all use the identical `max(100, limit*5)` base formula — keep them in lockstep, and don't hand-tune any single caller's `k` to 'fix' short results (fix `SearchByVector` instead; per-caller divergence drifts). **sqlite-vec hard-rejects `k > 4096`** ("k value in knn query too large"); `Vec0MaxK = 4096` caps the escalation and clamps every KNN call. Escalating deeper than the old fixed `k` changes which candidates feed RRF on corpus-selective filters, so re-baseline (`mailvec eval`) after touching this.
- **Date filtering uses `datetime()` for comparison.** Stored `date_sent` is `DateTimeOffset.ToString("O")`, which mixes UTC `Z` and `+HH:mm` offsets. Wrapping both sides in SQLite's `datetime()` normalises them; a raw string compare would silently miss matches across offsets. Messages with NULL `date_sent` are excluded when any date bound is set.
- **One row per message** in vector search results. `VectorSearchService` uses a window function (`ROW_NUMBER() OVER ... rn=1`) so the same message can't appear twice from different chunks. Hybrid search relies on this invariant when fusing. Attachment matches don't add rows — the chunk's `source` + `attachment_id` ride along as `VectorHit.ChunkSource` / `MatchedAttachment*`.
- **RRF k=60** in `HybridSearchService.RrfK` — standard from the literature. Don't tune without benchmarking against a real query set.
- **`get_thread` resolves via thread_id, with a special case for lone messages.** `MessageRepository.GetThreadByMessageId` first looks up the requested message, then queries by its `thread_id`. If `thread_id` is NULL (a message that wasn't part of any reference chain), the method returns just that one message rather than empty. Don't "fix" this to require non-null thread_id — singletons are common (notifications, marketing).
- **`SchemaMigrator.EnsureUpToDate()` runs at MCP startup.** If the configured `DatabasePath` doesn't exist, the migrator silently creates a fresh empty schema there. When debugging "no results", first check `mailvec status` to confirm message counts on the same path the MCP server resolved.

## MCP API stability

The MCP tool surface is a **wire contract** — tool names, parameter names, and response field names are locked, and a rename breaks every client at once. The full locked list, plus the `McpSurfaceTests` enforcement mechanism and the transport quirks (stateless HTTP, stdio, Claude Desktop's sandbox), live in [`src/Mailvec.Mcp/CLAUDE.md`](src/Mailvec.Mcp/CLAUDE.md) and load automatically when you work in that project.

Source-of-truth for version: the repo-wide `<Version>` in [Directory.Build.props](Directory.Build.props) — one version stamps all four .NET binaries, kept in lockstep with `manifest.json` and the tray's `MARKETING_VERSION` (project.yml) by `ops/release.sh`, which is the only sanctioned bump path (`ops/build-mcpb.sh --bump` delegates to it; the non-bump MCPB build fails on drift). Read at runtime via `Assembly.GetEntryAssembly().GetName().Version` in `Program.cs::ConfigureServerInfo`; printed by `mailvec status`. Tag releases `v<version>` after the bump commit (release.sh prints the commands; `publish-images.yml` refuses a `v*` tag that doesn't match `<Version>`). Patch for anything; minor for a tool-surface change or schema migration. `SchemaMigrator.EnsureUpToDate` refuses to run an older binary against a newer DB (downgrade guard) — don't weaken it to a warning; the older binary silently lacks newer invariants (e.g. pre-v7 never bumps `embed_epoch`).

Before any change that could shift retrieval ranking (chunk size, RRF k, embedding model, tool-shape tweaks), capture an eval baseline (`mailvec eval --json baselines/<date>.json`) — see `baselines/README.md`. Without it, a quality regression that "looked like a refactor" is invisible until the user notices.

## Operations

- **`/health` is HTTP-mode only.** Stdio has no analog — Claude Desktop sees failures via the `initialize` handshake instead. Endpoint is registered before `MapMcp()` in `Program.cs::RunHttp` and bypasses MCP framing. Logic lives in `Mailvec.Core/Health/HealthService.cs` so the CLI can reuse the snapshot if needed. Returns 503 (not 200) when degraded ("degraded" = Ollama unreachable OR `metadata.embedding_model` disagrees with `Ollama:EmbeddingModel` OR the embedder is stuck — see `HealthService.IsStuck`); don't broaden the degraded set without thinking about false-positive paging cost. Auth boundary is "bind to 127.0.0.1" plus, on the container, the Cloudflare Access gate — optionally validated at the origin via `Mcp:Access` (off by default; `docs/security.md` "Origin authentication"). See the README Security model section before changing the bind address.
- **Ollama ping is bounded by a 5 s linked-CTS, not the embedder's 60 s timeout.** `OllamaClient.PingAsync` wraps the call in `CancellationTokenSource.CreateLinkedTokenSource(ct)` with `CancelAfter(5s)` — 5 s allows a cold model load on the first probe; warm probes return in milliseconds — and only swallows `OperationCanceledException` when the *outer* token wasn't cancelled. This is already at the sensible ceiling; don't raise it further (the tray polls /health every 5 s).
- **Log rotation is in-process (Serilog), not external.** Each launchd-installed service wires `SerilogSetup.Configure(...)`. Output: `~/Library/Logs/Mailvec/mailvec-<service>-<YYYYMMDD>.log`, daily rolling, also rolls if a single day exceeds 10 MB, 14 most recent files retained. Rolling is atomic *within a single writer per service* — true because the launchd HTTP MCP / indexer / embedder are each one process. **MCP in stdio mode does NOT write to this file** — Claude Desktop spawns one `Mailvec.Mcp --stdio` child per session (main chat + one per Cowork session), all named `Mailvec.Mcp`, concurrent with the launchd HTTP MCP. If they shared the rolling file, they'd race on size-cap rolling and retention prune: `shared: false` only enforces single-writer on Windows, but POSIX `O_APPEND` happily admits multiple writers and Serilog swallows the resulting `IOException`s via `SelfLog`. Stdio output goes to stderr only; the client captures it (Claude Desktop → `~/Library/Logs/Claude/mcp-server-mailvec.log`). Source: [`SerilogSetup.Configure`](src/Mailvec.Core/Logging/SerilogSetup.cs) wraps the file sink in `if (!stdioMode)`.
- **`MAILVEC_LAUNCHD=1` suppresses Serilog's Console sink.** Set in the launchd plist `EnvironmentVariables`. Without it, every log line writes to both the rolling file and stdout/stderr, where launchd captures it into `StandardOutPath`/`StandardErrorPath` — doubling disk usage. With the env var set, the launchd-captured `<service>.launchd.log` only catches things that bypass `ILogger`: pre-Serilog startup output, unhandled native stderr, panics.

## mailvec CLI shim

`ops/install.sh` publishes the CLI to `~/.local/share/mailvec/cli/` (alongside the three .NET services) and drops a shim at `~/.local/bin/mailvec` that execs `dotnet ~/.local/share/mailvec/cli/Mailvec.Cli.dll`. The shim sets `DOTNET_ROOT` + `PATH` so it works under Claude Desktop's sanitised-PATH child processes too.

- **Why a shim, not a symlink to the .dll**: .NET requires `dotnet <dll>`, not direct invocation. The shim hides that detail.
- **Why a shim, not `/usr/local/bin/mailvec`**: writing to `/usr/local/bin` needs sudo or a Homebrew tap. `~/.local/bin/mailvec` is sudo-free and the tray UI's [`CliRunner.swift`](src/Mailvec.Tray/Sources/CliRunner.swift) prefers it anyway.
- **Re-run `ops/install.sh` (or `ops/redeploy.sh cli`) after CLI source changes** — the shim is generated at install time and points at a published .dll, not the working-tree source. `dotnet build` alone won't update it.
- **Eight tray buttons depend on this**: Dashboard's Doctor, Embedding's Audit/Reindex, Advanced's Doctor/RebuildFTS/Checkpoint/Audit/Purge. All route through `CliRunner.runInTerminal(...)`.

## Status

End-to-end working. **The author's deployment is the Docker stack on a Proxmox homelab, exposed via Cloudflare Tunnel + Access Managed OAuth** — every Claude surface (Code, Desktop, iOS, claude.ai) uses that one remote connector, and the Claude Desktop MCPB/stdio path is retired as a transport.

**This Mac is a development machine, not a deployment** (decommissioned 2026-07-16): no launchd agents, no mbsync, nothing on `127.0.0.1:3333`. Its `archive.sqlite` is a **frozen corpus** for eval/ranking work — see [`docs/contributing/local-dev-dataset.md`](docs/contributing/local-dev-dataset.md) for the workflow and the refresh procedure.

> ⛔ **Do not reinstall the agents, and do not run `ops/install.sh` / `install-all.sh` / `redeploy.sh` here — not even "just to test that it works."** This has already happened once: on 2026-08-04 all four agents were found installed and three running, having been reinstalled by an agent as part of a test, with mbsync pulling live mail again. **Installing them is what the warning is about — the install IS the damage**, so there is no version of "I'll put it back afterwards" that avoids it.
>
> What it costs: mbsync resumes and the indexer ingests, so the corpus stops being the one the `baselines/` numbers were measured against and every eval comparison silently drifts against a moving target. The 2026-08-04 incident moved ~136 messages before it was caught.
>
> **Verify before you touch anything** — `launchctl list | grep mailvec` should print nothing, and `~/Library/LaunchAgents/com.mailvec.*.plist` should not exist. **If they are back, tear them down with `ops/install.sh --uninstall`** (not `ops/stop.sh` — that leaves the plists, so they re-bootstrap at login) and say so, because the corpus has moved.
>
> To exercise service code here, run it directly against the archive: `dotnet run --project src/Mailvec.<svc>`. That is the supported path and it needs no agents.

The macOS launchd install, the MCPB bundle, and the tray all still build and are supported for anyone wanting a local single-machine setup — that support is what the paragraph above is protecting, not contradicting; it just isn't exercised by installing them *on this machine*. The tray is local-dev-only in practice (it polls `/tray/*`, which the container disables via `Mcp:EnableTrayEndpoints=false` and the tunnel 404s — the surface returns mail content, so it stays off any internet-fronted deployment).
